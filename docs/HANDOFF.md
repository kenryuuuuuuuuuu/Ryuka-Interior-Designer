# 引き継ぎドキュメント（Claude.ai → Claude Code）

このドキュメントは、Claude.ai上での長時間セッション（2026-08-13、間取り・ドア・窓の座標確定〜rooms/walls移行まで）で積み上げた文脈を、Claude Codeでの作業に引き継ぐために書いた。**新しくこのリポジトリを開くエージェントは、作業を始める前にこのファイルを読むこと。**

## 1. このプロジェクトの目的（なぜこれを作っているか）

施主が2027年4月の竣工を予定している新築住宅（主居＋民泊棟の二世帯構成）の内装を、着工前に検証・意思決定するためのデジタルツイン。最終的な狙いは3つ。

1. **寸法・間取りの精度を上げること。** 施工会社の実施図面はCAD原本ではなくスキャンPDF/画像しかない。断面図もない（天井高が図面から読み取れない）。この白模型は、複数の参考資料を突き合わせて壁位置の矛盾を洗い出す検証ツールとして機能している
2. **施工会社への要望を視覚的に伝えること。** 平面図の口頭説明より、3Dモデルの方が伝わる
3. **将来的な意思決定の土台。** 家具配置・コンセント/照明位置・内装の質感検討を、この骨格の上に積み上げていく

**Three.js vs Blenderの位置づけ**：Three.jsは「寸法検証・骨格確認」に強く、実際にその通り機能した。一方「本物のような質感」（施主が当初イメージしていたゴール）は、Blenderの方が労力対効果で有利という評価を、このセッション中に伝えている。現時点でどちらに倒すかは未確定（本ドキュメント末尾の「未解決事項」参照）。

## 2. データの作り方（なぜこの数値なのか）

**ここが一番失われやすい文脈なので、必ず読むこと。**

### 2.1 情報源の優先順位

1. 施工会社の実施図面（Ver5、配置図・求積図・平面図・立面図の4葉。断面図はない）
2. `Ryuka-Landscape-Designer`リポジトリ（外観モデル、外皮の階高・軒高が実施図面と検算済みで確定）
3. マイホームクラウド（間取り作成サービス）の間取り画像。**面積・寸法線は信頼できるが、天井高・床高は物理的に矛盾する値を含んでおり、一切使用していない**
4. 上記から読み取れない部分は、910mmグリッド（尺モジュール）を前提に、面積からの逆算や画像のピクセル解析で補完

### 2.2 手法：画像のピクセル解析

CAD原本がないため、施主がマイホームクラウドの画面やこの白模型のスクリーンショットに赤線・青線を描き込み、それを都度ピクセル単位で解析して実寸に変換する、という作業を数十回繰り返して座標を確定した。

**技術的な教訓**：

- **キャリブレーションは離れた2点を基準にする。** 近接した2点（間隔0.9m程度）で比率を出すと、数ピクセルの誤差が大きく増幅される。過去に一度、この理由で壁位置を誤って「訂正」し、さらにそれを再訂正するという手戻りが発生した
- **赤/マゼンタ/水色などの色は、既存の描画要素（ドア=マゼンタ、窓=水色）と被ると誤認識しやすい。** ユーザーの手描き線は「純色（例: R<80,G<130,B>180）」、モデルの描画要素は半透明のブレンド色になることが多く、RGB値で判別可能
- **求積図の外形区分（A1〜A4ゾーン）と、実際の部屋割りは一致しない。** 例えば「LDK」は外形ゾーンをまたいで存在し、北側の壁が3段階（z=2.730→2.275→1.820）の階段状になっている実例がある

### 2.3 確度（status / conf）の運用

`高`/`中`/`低`（JSON側では`verified`/`derived`/`estimated`）の3段階。

- `高`：実施図面と複数資料の相互検算で確定、または施主が画像に描いた線をピクセル解析して確定
- `中`：1辺は確定だが、もう1辺は面積からの逆算など間接的な根拠
- `低`：目視のみ、または未検証

現時点で1F・2Fの全部屋・全ドアが`高`。窓は施工会社図面ベースの確定データが大半だが、セッション中に位置を調整した箇所がある。

## 3. 見つかった不具合と教訓（同じ轍を踏まないために）

このセッション中に発見・修正したバグを列挙する。多くはThree.js特有の癖なので、Web表示ロジックを触る際は要注意。

| 症状 | 原因 | 対処 |
|---|---|---|
| 一部の部屋だけ色が薄い/白く見える | 半透明オブジェクトの`depthWrite`がデフォルトで有効なため、重なった別の半透明レイヤーが下の色を隠す | 全ての半透明マテリアルに`depthWrite:false`を設定 |
| 部屋の輪郭線がチラつく/薄い | 隣接する2部屋が同じ境界線を別々に描画し、Z-fighting | 輪郭線マテリアルに`depthTest:false`を追加し、`renderOrder`だけで描画順を決定させる |
| 矩形とL字ポリゴンで色味が違って見える | `MeshStandardMaterial`は光源方向・法線で陰影が変わる。ポリゴン(ExtrudeGeometry)と矩形(BoxGeometry)で法線の向きが揃わないと陰影差が出る | `MeshBasicMaterial`（ライティング非依存）に変更 |
| 2F西面の窓がx=0（1F西端）に誤配置 | `face:'W'`の開口部は常に絶対西端(x=0)に固定する実装だった。2F自体の西壁はx=12.740 | 開口部データに`x`フィールドを追加し明示指定できるよう改修 |
| ドアマーカーが壁からわずかにはみ出す | 部屋の境界ぎりぎりにドアを配置すると、数cmの計算誤差で越境する | ドアは壁の両端から余裕（0.05m以上）を持たせて配置。`tests/validate_house.py`に「全ドアが対応する壁の範囲内に収まっているか」の機械チェックを追加済み |
| 2つの窓が繋がって1本の長い窓に見える | 同じ壁(x=12.740)上に配置した2つの窓のz範囲が一部重複していた | 個別の窓のz範囲が重ならないことを確認してから配置する |
| rooms→walls変換で、複数ゾーンにまたがる壁が外壁として除外されない | 「壁の区間全体が1つのfootprintに収まるか」で判定すると、2つの隣接footprintにまたがる外壁を見逃す | 区間の「引き算」方式（該当座標の外皮区間を全て集めてから差し引く）に変更 |
