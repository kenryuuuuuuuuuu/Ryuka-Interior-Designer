## 1. ローカル入力と確度

既存build内の敷地関連ファイルと資料の所在をまず確認し、サンプル/テスト/実敷地候補を区別します。実座標や個人資料の本文を公開Git/報告へ転記しません。ファイル名だけで実敷地と認定しません。確定できない位置・真北・周辺寸法は施主へ不足情報をまとめて報告し、サンプルで機能実装を継続できます。

敷地は既存validate_siteの1.0.0形式（latitudeDeg/longitudeDeg/planNorthAzimuthDeg/locationStatus/northStatus/note）を維持します。建物寸法や器具位置をこのファイルへ複製しません。位置・方位のverifiedは入力根拠の確認であり、照度校正の意味ではありません。

UE「内装比較」の採光メニューからローカル敷地JSONを読み込めるようにし、位置・方位・確度・根拠を通常UIで確認できるようにします。最初の敷地入力を作る手順も簡単なフォーム/ダイアログで用意します。既存Windowsダイアログの再利用でも構いません。普段の日時変更にJSON編集やPythonコンソールを要求しません。入力ファイルは新規作成を基本とし、既存を黙って上書きしません。

読み込んだ敷地はプロジェクト内のローカル `site.local.json` にスナップショットとして保持します。生成プロジェクトと保存案はbuild内限定です。公開ソースのdataへ実座標を追加しません。設定変更をキャンセルしても以前の正常な条件は保持します。

## 2. 日時ケースと比較状態

既存sun-cases.jsonとsolarケース構造を再利用します。日時には必ずUTCオフセットを付けます。初期UIはJST（+09:00）を明示し、年/月日/時刻を入力できるようにします。任意日付に加え、季節の代表日（例3/21・6/21・9/21・12/21）と9/12/15時を提供します。これらの日を毎年の厳密な春分/至日だと呼びません。

適用可能な太陽高度は現行[1,89]度を維持します。範囲外は表示して理由付きで適用不可にし、昼の最小値へ丸めて夜を表現しません。夜間条件はW06で設計します。

siteSHA256は既存make_caseの計算規則を使います。現在のsite.local.jsonがある場合、日時ケースのハッシュ・日時・計算角度がその入力と対応しているか共通検証で確かめます。敷地/真北を変えたらケースを再計算し、旧solarの来歴を付けたまま角度だけ変えません。手動角度へ変更したら既存通りsolarを解除します。

study-stateは既存1.1.0＋solarを基本に維持し、不要に別の比較状態を追加しません。sunLuxと露出は現在の指定値を保持します。日時から自動的に実照度を計算したとはしません。UI/記録には「日差し位置の比較・光源強度固定・照度未校正」と表示します。

旧案にsite.local.jsonがなくても有効なsolar/sun-casesがあれば既存ケースを表示・適用できます。ただし「敷地原本なし・新日時計算には入力必要」と案内します。旧データから緯度経度を逆算したり、仮の値を黙って補いません。

## 3. 日時比較と操作

W04の仕上げA/Bと別の「日時比較」を追加します。比較開始時の面別仕上げ、基準variant、カメラ位置/向き/画角、露出、sunLux、contextを固定し、選んだ2日時の太陽角度/solarだけを切り替えます。開始前状態へ戻す操作を用意します。

両日時/来歴を適用前に検証し、途中で半分だけ比較開始した状態にしません。画面で日時・手動/日時モード・方位/高度・露出・位置/真北の確度・context有無を確認できるようにします。詳細の個人情報はローカルの詳細画面に留めます。W04の非阻害残件であるA/B両案の面参照事前確認も、共通の適用前検証を整理する際に含めてください。

UEエディタで日時選択し、既存の別ウィンドウ内覧でその条件を確認する流れで十分です。内覧中の独自日付ピッカーは不要です。内覧HUDに日時由来か手動かを示し、F5/F9でsolarと面別仕上げを保持します。手動太陽変更は日時表示を解除します。

比較画像の出力は既存capture/compareを利用します。現compareはvariantとの積を撮影するため、日時比較では面別上書きを含む現在の仕上げを固定できるモードを加える等で対応します。最初は2日時の画像とHTML/JSON記録で十分です。比較終了時の復元を維持します。UE埋め込みPythonのsys.executableで外部Pythonを起動しないこと。既存共通関数または明示した実行環境を使います。

## 4. 周辺遮蔽と建物の前提

既存site-context.jsonのbox形式を使います。boxはsource位置・GL基準の中心/寸法/回転であり、真北座標のつもりで回転し直しません。主要な隣棟・塀の入力根拠を表示し、未確認ならestimatedとします。

context変更は実際の幾何を再生成/再取込してから新しいハッシュを保存します。ファイルだけを差し替えて現在のシーンと一致したことにしません。既存のbuild-unreal-study --context経路を利用して構いません。遮蔽物あり/なしの動作確認は別の出力プロジェクトで同じ日時・画角・仕上げ・露出に揃えます。W04の「異なるcontextの案を現在シーンへ適用しない」原則を壊しません。

窓・庇・屋根・ガラスを短く棚卸しし、「正本あり/生成対応/仮定・未対応」を表にします。ゲストLDKの主要な日影を妨げる明白な欠落だけを必要最小限で直します。屋根全体の作り直しや新しいガラス透過モデルは今回の必須条件にしません。ガラスの影/透過近似は表示し、現実の透過率を保証しません。実敷地確認を妨げる形状不足は残件と影響を明記します。

## 5. 保存と再生成の契約

site.local.jsonを任意の案同梱ファイルとして既存保存/一覧/読込/refreshへ接続します。ALLOWED_SCENARIO_FILESやコピー経路・hash検証を更新します。新しい独立DBは作りません。保存案の各ファイルのハッシュと、solar.siteSHA256による敷地の意味上のハッシュを混同しません。

案読込では同梱site/ケース/状態の対応を検証してから採用します。contextは現在の実幾何に一致が必要です。地点・真北だけを切り替える場合も、明示的な案/敷地読込を通し、UIに適用した入力を表示します。日時だけの比較には同一siteを使います。

--scenarioはその案の状態/site/sun-cases/contextだけを使い、現在正本の建物へ適用します。--previous側の別敷地を混ぜません。旧案のsite欠落は許容し、現在siteが存在するのに状態/ケースと矛盾する場合は理由付き停止です。直接buildへは必要なら--site引数を追加します。

Blender出力にも保存した日時のplan方位・高度を反映するよう状態引数の読込を確認します。現在はvariant/surfaceOverridesだけを使用する箇所があるため、日時条件がUEだけで反映された状態を同条件と扱わないこと。レンダラー間の画素・露出一致は要求しません。

## 6. 代表検証と完了条件

1. ローカル入力から2日時を選び、視点・画角・露出・sunLux・面別設定が不変で日差しだけが変わることを実DX12画像2枚と条件記録で確認します。代表日時の角度は既存テストと、同じ関数を呼ぶだけではない既存の参照値で照合します。
2. 主要な遮蔽boxの有無で影が変わる代表例を確認します。実資料がなければ架空の検証物と明記します。全周辺物/全季節の網羅撮影は不要です。
3. 名前付き案保存→再読込→--scenarioの完全refreshを1回通し、site/solar/context/面別仕上げの対応を確認します。内覧保存復帰はこの成果物で代表1回確認します。
4. siteとケースの不一致または必須入力不足を1例、範囲外時刻を1例案内します。元の案を変更せず、通常条件へ戻せることを確認します。

関連テスト・house検証・web-data --checkを実施します。W04の受入済み材質テスト一式や多重障害の再実行は要求しません。実敷地入力が未確定なら「機能確認済み/実敷地確認待ち」と分けて報告します。機能が完成した段階で資料待ちだけを理由に作業を無限に続けません。
