# W04 面別の仕上げ編集・比較・保存復元

状態：READY。実装担当：Claude Code（Sonnetを基本とします）。設計・レビュー：GPT。

## 目的と一括の完了単位

ゲストLDKで対象の壁・床・天井を選び、仕上げや色を変え、同じ視点・露出・太陽条件でA/Bを比較し、保存・再起動・現在の正本からの再生成後にも復元できるようにします。データ、Blender、UE、編集UI、保存と比較まで本タスクでつなぎます。W04-A/B/Cへの分割や内部工程ごとのレビュー待ちは不要です。

操作範囲は登録済みゲストLDKです。全館の面登録、VR、任意画像のテクスチャ取込、実商品カタログ、家具配置案の複数管理、植物/布の磨き込み、採光校正は含めません。編集はUEエディタの既存「内装比較」から行い、内覧は既存の歩行モードを使います。歩行中の独自編集パネルまで二重に作る必要はありません。

## 1. 永続IDから実際の仕上げ面への対応

surface-registry.jsonのIDを保存キーにします。登録座標は識別用で、描画形状は常に現在のhouse/openings/生成幾何から作ります。生成メッシュ名・slot番号・polygonの配列順を永続キーにしません。

- wall：当該roomの内側を向いた壁の主面だけを対象とします。共有壁の反対側、壁厚の端面、開口の見込み、窓枠・建具は変えません。1つのsurface IDが窓・ドア上下左右の複数片へ対応することを許容します。
- floor：部屋polygon内の上面だけです。現在のfootprint単位のslab全体へ部屋の仕上げを付けて隣室を変えないこと。
- ceiling：当該部屋の天井下面です。勾配・平天井が複数片でも同一IDに対応できます。梁、段差の立ち上がりは対象外です。
- 部屋境界が開放され実壁がない箇所は、壁を新設せず `no-surface` として扱います。未登録の家全体は既存の材質・形状を維持します。

実装は既存の実壁/天井/床ポリゴンと部屋境界を対応させ、必要な主面を別material slotへ区分する方式を優先します。部屋境界での分割が必要なら元の表面を置き換えるように分割し、重複した同一平面や余分な衝突体を重ねません。壁全体のprismを別色にする近道は不可です。既存の開口切欠き、壁厚、勾配、日影用の外皮を維持します。共有壁の所有側はroom polygonの内側で判定し、名前の「北/南」から推測しません。

Blender出力に `surface-bindings.json` を加えます。schemaVersion=1.0.0、surfaceId→roomId/kind/状態（bound/no-surface）/生成meshとmaterial slotの一覧を記録します。必要な根拠・制限も記録し、manifestのartifactsに含めます。1slotへ異なるsurface IDを割り当てたらエラーです。GLBに専用slot/material名を持たせるなど、インポート後に名前が正規化されても対応が一意に検証できる方式にします。GLB extrasが自動でActorへ残ると仮定しません。

UE importでは現在のActor/Component/slotへ解決し、プロジェクトの `surface-bindings.json` に現在の対応を保存します。元GLB側のファイルはSourcePackage内へ残します。旧study-bindings.jsonの全体ロール対応も維持します。両者の役割は「全体の基準適用→面別上書き」です。幾何インポートに存在しないActor/slotをbound扱いにしません。

## 2. 比較状態の契約と互換性

面の上書きは別の独立保存ファイルへ分散せず、既存study-state.jsonおよびSaved/walkthrough-state.jsonの比較状態に含めます。新規保存はschemaVersion=1.1.0とし、1.0.0を上書きなしとして読み込めます。scenario.jsonの外側は既存1.0.0を維持できます（格納ファイルのハッシュ方式はそのまま）。

新しいフィールド例：

```json
{
  "schemaVersion": "1.1.0",
  "surfaceOverrides": {
    "surf-guest-wall-003": {"variant": "warm", "colorHex": "c7beb0", "roughness": 0.8},
    "surf-guest-floor-001": {"variant": "reference"}
  }
}
```

これは追加フィールド例です。roomId・基準variant・camera・太陽・露出等の既存必須フィールドは従来通り保持します。surfaceOverridesは辞書で新形式では必須、旧形式は空へ正規化します。

各値のvariantは既存natural/warm/referenceから選び、対象kindの既存ロール定義を使います。colorHex（6桁sRGB、#なし）とroughness（有限数0〜1）は省略可で、指定時だけそのプロパティを上書きします。未知variant・未知フィールド・型不正を黙って無視しません。単位や色変換は既存マテリアルと統一します。任意の新しい模様定義の編集は不要です。referenceの石調床・木板天井など既存模様とスケールは再利用します。

優先順位：基準variantを全体へ適用→surfaceOverridesを対象面だけへ適用。基準variant切替時も明示上書きは残し、UIにその旨を示します。「対象を基準に戻す」で該当キーを削除し、「上書きをすべて解除」で空にします。共有material assetを直接変更せず、対象ごとのinstance等で隔離します。全体variantがこれまで通り自宅側へ影響する挙動と、面別操作の影響を混同しません。

Python/UE editor/C++の状態検証・適用・保存を全て更新します。旧scene_state()の「mixed/custom finishesは保存不可」という判定は本機能と矛盾するため、管理された面別状態を検証して書き出す方式に置き換えます。Actor material名からvariantを無理に逆算しません。直接手作業で変更された未管理材質まで復元する義務はありませんが、保存できない状態なら理由を表示します。

無効なID・room不一致・no-surfaceへ上書きがあるときは対象IDと理由を案内し、適用/再生成を停止します。保存済み案を削除・自動修正せず、そのまま残します。JSONの構造検証と現在モデルへの参照検証を分け、孤立参照を持つ案でも一覧と修正案内は表示できるようにします。

## 3. 保存・生成パイプライン

既存の保存成否・バックアップ復旧の仕組みは維持し、新しい状態フィールドを落とさず往復させます。F5/F9、再起動、editor保存、名前付き案保存、--scenario再適用の全経路が対象です。ネイティブの仕上げ切替でも面別上書きを維持します。状態適用は必要な対象/材質を先に検証してから行い、エラーで半分だけ変更された状態を残さないこと。

refreshのretained/scenario_inputsが選んだ状態を、Blenderの生成へも渡します。現在はvariantだけが渡される経路があるため、CLI引数または検証済み状態ファイルを追加し、Blender保存物とUEの仕上げが同じ指定を反映するようにします。両レンダラーの画素一致は求めません。直接build時は上書きなしを既定値とします。

未解決の登録/存在しないIDはBlender前に停止します。実幾何を作らないと確定できないno-surfaceはBlender段階で検出し、UE起動前に案内できれば十分です。可能なら既存の純幾何ヘルパーで事前確認しますが、そのためだけの幾何処理の二重実装は不要です。

新モジュール・登録・対応manifestを既存入力ハッシュ、原本コピー、artifact検証へ含めます。状態ファイルから過去のhouse形状をコピーせず、現在の正本へ案の仕上げを適用します。解決対象は現在のsurface IDです。

## 4. 施主向け操作

既存UE「内装比較」から開ける簡単な編集パネルを用意します。Slate等の方式は既存プロジェクトに合わせて裁量とします。普段の操作にPythonコンソールやJSON手編集は不要です。

- ゲストLDKの面一覧：日本語label/kind、選択中の対象、no-surfaceの案内。IDは詳細表示で十分です。
- 対象選択の確認：短時間のハイライトまたは輪郭表示で位置が分かること。ハイライトは保存・撮影・案比較の材質に混ざらないこと。レイクリック選択の追加は任意で、一覧選択だけでも完了です。
- natural/warm/referenceの仕上げプリセット、任意の色、roughnessを設定・適用。「対象を基準に戻す」「上書き全解除」「比較条件とレベルを保存」を用意します。
- 「部屋全体へ適用」は、その部屋のboundな登録面へ種別に対応するプリセットを一括適用します。未登録部分まで変更済みとは表示しません。必要なら壁一括/床/天井を分けて表示して構いません。

保存済み案の名前付き一覧・保存・読込は既存W03-Aのパッケージと検証を再利用し、パネルから実行できるようにします。既存CLIも維持します。出力はローカルbuild内の新規ディレクトリ、既存案は上書きしません。フォルダ選択等の方法は裁量です。

A/B比較では2つの保存済み案を選択し、「比較開始時の現在の視点・画角・露出・太陽条件」を固定したまま、案の基準variantとsurfaceOverridesだけを切り替えます。案に保存されたカメラや太陽まで切り替える通常の案読込と操作を区別します。比較中は使用した固定条件と案名を表示し、比較終了で開始前状態に戻せるようにします。切替は再生成なしで動作させます。周辺遮蔽設定等が現在プロジェクトと異なる案は、通常再生成が必要と案内し、同条件比較と偽らないこと。

## 5. 検証・受入（代表例だけ）

1. 実ゲストLDKの壁1面を目立つ色へ変更し、窓で分かれた該当面へ反映、他面・共有壁の裏側・隣室床が不変であることを確認します。共有壁の裏側は必要ならエディタの確認視点で見ます。実データに対応がない条件は小さい幾何fixtureで補えば十分です。
2. 床・勾配天井のプリセット変更、対象の解除、部屋への一括適用を代表1回確認します。開口が埋まらず、床や壁の重複によるちらつきがなく、既存歩行が使えることを短く確認します。
3. A/Bを同条件で切り替え、名前付き保存、F5/F9またはeditor→歩行保存の代表往復、再起動復元を確認します。1回の完全refresh（Blender→UE）に--scenarioを使い、指定した面の仕上げとカメラ/太陽条件が引き継がれることを確認します。旧1.0.0状態は関連テストで読み込み確認します。
4. 簡単な異常系として消えたsurface IDまたはno-surfaceへの設定を1件、型不正を1件確認し、元の案が保たれることを確認します。多重障害・全分岐証明・W02障害注入一式の再実行は不要です。

純Pythonの変換/優先順位/互換性/参照の代表テスト、house検証とweb-data --check、変更に必要なビルドを実施します。実描画を変える今回はDX12で代表的な操作・画像を確認します。全操作の自動OS入力化や大量の画像生成は不要です。Blender/UEでの同色指定は比較し、色管理の差による画素一致を完了条件にしません。
