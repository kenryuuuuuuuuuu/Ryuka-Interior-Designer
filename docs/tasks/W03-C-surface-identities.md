# W03-C 面の永続IDと形状変更時の対応契約

状態：READY。実装担当：Claude Code / Sonnet。仕様・レビュー：GPT。

## 成果と範囲

ゲストLDKの部屋側の境界面・床・天井に明示的なIDを登録し、現在の正本へ解決できるかを軽い処理で確認できるようにします。W04が仕上げ設定の対象として参照するデータ契約です。

今回は識別・検証・パッケージへの同梱までです。面ごとの材質適用、UEでの面選択、メッシュ分割、C++変更はW04です。「面IDがUEの実メッシュへ接続済み」とは報告しません。部屋境界には開放部分もあるため、登録は実在する塗装面の存在を保証しません。

作業場所は `build/worktrees/visual-twin`、ブランチは `feature/visual-twin-foundation` を継続します。仕組み変更をmainへ直接入れません。着手時HEADをBASEに記録してください。AGENTS.md、BACKGROUND.md、DEVELOPMENT_WORKFLOW.md、W03-B仕様・レビュー、blender/build_interior.py、scripts/source_changes.py、scripts/build-visual-twin.pyを参照してください。

## 設計判断

現在のwall番号やメッシュ名は配列順・開口分割で変わるため永続IDにしません。house.jsonのpolygon形式も変更しません。Three.js側との競合を抑えるため、独立した `data/visual/surface-registry.json` に明示的なIDと参照先を保持します。このファイルは面の識別設定であり、建物形状の新しい正本ではありません。描画形状は常にhouse.json等から取得します。

自動追跡より誤適用を防ぐ単純な契約を優先します。壁を動かしたときは登録の参照座標を明示的に更新します。同じ意味の面として維持する場合はIDを維持できます。通常生成時に座標の近さでIDを付け替えたり、登録を自動更新したりしません。

## 登録形式 v1

schemaVersionは1.0.0、surfaces配列を持ちます。各レコードは以下です。

- id：手動で確定した一意のASCII文字列。例 `surf-guest-wall-001`。番号は初期命名にすぎず、並び替えで再採番しません。
- roomId：house.rooms[].id。
- kind：wall / floor / ceiling。
- label、note：施主向けの名称と対応の判断根拠。形状の確度はhouseのstatus/noteを解決結果へ引き継ぎ、登録IDを付けたことを施工確認済みという意味にしません。
- wallだけにedge：`[[x0,z0],[x1,z1]]`。部屋polygonの辺の両端をsource座標・メートルで記録します。端点順は識別に影響しません。

初期登録はroom-1f-06の6辺と床1面・天井1面です。寸法・家具・間取りは変更しません。床・天井のIDは部屋全体を対象とし、勾配天井の複数生成片も将来は同じIDへ属せます。梁・段差の立ち上がり・窓枠・開口の見込み・巾木は対象外です。

共有壁の両側は異なるroomIdと異なるsurface IDです。同一室の同一辺への重複登録、同一室のfloor/ceilingの重複、idの重複は拒否します。他室が未登録でもエラーにはしません。

## 解決と変更の意味

共通の純Pythonモジュール（例 scripts/surface_registry.py）を作ります。

wallは指定roomのpolygonに一致する辺を探します。端点逆順・polygonの開始頂点変更・周回方向反転を許容し、座標許容差は1e-6mです。配列indexは解決結果に含めても構いませんが、永続参照には使いません。辺の一部だけの一致、近傍探索、方位だけでの一致は不可です。複数一致は曖昧としてエラーです。

- ラベル・家具・開口の変更：surface IDを維持します。窓移動でできる複数の壁片は同じ部屋境界面に属するという契約です。
- 壁位置の変更：旧edgeはunresolvedになります。登録edgeを現在の辺へ明示更新し、同一面ならID維持、別物なら新IDとします。自動修復は不要です。
- 辺の分割・結合：旧面を自動で新しい複数辺へ継承しません。旧IDは未解決として案内し、登録変更で新IDへ置き換えます。旧IDは別の面に再利用しません。
- 部屋の削除・分割・結合：削除されたroomIdの登録は未解決です。新室へ名前や位置で転用しません。分割・結合で意味が変わる部屋には新roomIdを付ける運用を文書化します。
- floor/ceiling：同じroomIdなら現在の部屋形状へ追従します。単純な寸法・天井形状変更でIDを変えません。W03-Bの部屋差分が変更案内になります。

解決結果はschemaVersion、各面のid/roomId/kind/label/status（resolved/unresolved）、現在の辺または部屋polygonとceiling、形状の根拠・確度、issuesを持ちます。issuesは対象ID・ファイル・理由・修正案内を持ちます。登録座標から代替壁を作ることは禁止です。法線やUEマテリアルslotを推測して格納する必要はありません。

## CLI・既存処理との接続

`scripts/check-study-surfaces.py --output build/W03-C-check-v1` を追加します。出力は新規build内限定とし、surface-resolution.jsonとindex.htmlを生成します。HTMLは面一覧と部屋輪郭の簡単なSVG平面図で、各辺のラベル/IDと未解決を確認できれば十分です。床・天井は一覧表示します。Blender/UE起動は不要です。参照切れ・重複・不正形式は非0、正常は0です。JSON欠落や不明なschemaVersionを空の成功結果にしません。

W03-Bの共通事前確認へ登録の検証を接続し、現在の未解決登録はBlender前に停止して理由を案内します。重い処理を呼ばないテストには必要な登録fixtureを加えます。登録がない他室は停止理由にしません。

build-visual-twinのinterior生成でも同じvalidatorをBlender前に使います。通常の白模型だけの生成を、このvisual設定の不備で止める必要はありません。新モジュールを既存inputs()の入力ハッシュ/原本コピー対象へ含めます。surface-registry.jsonは現在のdata収集に含まれることを確認してください。既存SourcePackageのコピー経路でUE側にも元登録を引き継ぎます。新しい独自の履歴DBは不要です。

旧パッケージ・W03-A案は登録がなくても読めます。現在の登録を利用し、過去に面の仕上げが保存されていたと推測しません。既存のvariant・部屋全体の仕上げ・保存状態形式は維持します。比較元のsurface-registry欠落は移行上の警告だけで、現在の正しい登録を拒否しません。W03-Bの対象限定差分を全面的に拡張する必要はありません。

## W04へ引き継ぐ契約（今回は実装しない）

仕上げ設定はsurfaceIdをキーにします。解決された部屋境界と、実際の壁ポリゴン・開口・部屋側の向きから、当該室側の面だけへ適用します。現在の壁prism全体に一括設定すると隣室側まで変わるため、その実装は不可です。1つのIDから複数生成片への対応を許容し、内部片番号は保存しません。床も現在のfootprint単位のslabをそのまま部屋IDへ割り当てません。

実面との対応・材質slot分離はW04で詳細化します。開放境界など実面がない対象へ仕上げを指定したときは、対象なしと案内します。消えたIDを参照する案は未解決として保持し、別面へ転用・黙って削除しません。W03-Cでは未使用の将来用仕上げJSONや移行エンジンは作りません。
