# 背景・経緯（なぜこうなっているか）

このドキュメントは、プロジェクトの目的・データの作り方・過去に見つけた落とし穴を記録する。**新しくこのリポジトリを開くエージェントは、作業を始める前にこのファイルを読むこと。** 技術的な仕組み（正本・変更手順）は [ARCHITECTURE.md](ARCHITECTURE.md)、現在の進捗・未解決事項は [STATUS.md](STATUS.md) を参照。

## 1. このプロジェクトの目的（なぜこれを作っているか）

施主が2027年4月の竣工を予定している新築住宅（主居＋民泊棟の二世帯構成）の内装を、着工前に検証・意思決定するためのデジタルツイン。最終的な狙いは3つ。

1. **寸法・間取りの精度を上げること。** 施工会社の実施図面はCAD原本ではなくスキャンPDF/画像しかない。断面図もない（天井高が図面から読み取れない）。この白模型は、複数の参考資料を突き合わせて壁位置の矛盾を洗い出す検証ツールとして機能している
2. **施工会社への要望を視覚的に伝えること。** 平面図の口頭説明より、3Dモデルの方が伝わる
3. **将来的な意思決定の土台。** 家具配置・コンセント/照明位置・内装の質感検討を、この骨格の上に積み上げていく

**Three.js vs Blenderの位置づけ**：Three.jsは「寸法検証・骨格確認」に強く、実際にその通り機能した。一方「本物のような質感」（施主が当初イメージしていたゴール）は、Blenderの方が労力対効果で有利という評価を、2026-08-13のセッション中に伝えている。現時点でどちらに倒すかは未確定（[STATUS.md](STATUS.md) の未解決事項を参照）。

## 2. データの作り方（なぜこの数値なのか）

**ここが一番失われやすい文脈なので、必ず読むこと。**

### 2.1 情報源の優先順位

1. 施工会社の実施図面（Ver5、配置図・求積図・平面図・立面図の4葉。断面図はない）
2. `Ryuka-Landscape-Designer`リポジトリ（外観モデル、外皮の階高・軒高が実施図面と検算済みで確定）
3. マイホームクラウド（間取り作成サービス）の間取り画像。**面積・寸法線は信頼できるが、天井高・床高は物理的に矛盾する値を含んでおり、一切使用していない**
4. 上記から読み取れない部分は、910mmグリッド（尺モジュール）を前提に、面積からの逆算や画像のピクセル解析で補完

**PDF原本の所在**：上記1の実施図面PDF（`渡辺拳竜様邸新築工事.pdf`、Ver5・全4葉）は`docs/`に置いてあるが、施主の氏名・住所・電話番号を含むため`.gitignore`で除外しており、GitHub上には存在しない。ローカルのファイルシステムには残っているので、新しいエージェントは`docs/`配下を直接確認すること。この環境には`pdftoppm`（poppler-utils）が入っていないため、`pip install pymupdf`でPDFページをPNG化して読む方式を使った。

### 2.2 手法：画像のピクセル解析

CAD原本がないため、施主がマイホームクラウドの画面やこの白模型のスクリーンショットに赤線・青線を描き込み、それを都度ピクセル単位で解析して実寸に変換する、という作業を数十回繰り返して座標を確定した。

**技術的な教訓**：

- **キャリブレーションは離れた2点を基準にする。** 近接した2点（間隔0.9m程度）で比率を出すと、数ピクセルの誤差が大きく増幅される。過去に一度、この理由で壁位置を誤って「訂正」し、さらにそれを再訂正するという手戻りが発生した
- **赤/マゼンタ/水色などの色は、既存の描画要素（ドア=マゼンタ、窓=水色）と被ると誤認識しやすい。** ユーザーの手描き線は「純色（例: R<80,G<130,B>180）」、モデルの描画要素は半透明のブレンド色になることが多く、RGB値で判別可能
- **求積図の外形区分（A1〜A4ゾーン）と、実際の部屋割りは一致しない。** 例えば「LDK」は外形ゾーンをまたいで存在し、北側の壁が3段階（z=2.730→2.275→1.820）の階段状になっている実例がある

### 2.3 確度（status / conf）の運用

`高`/`中`/`低`（JSON側では`verified`/`derived`/`estimated`）の3段階で運用している。定義は[README.md](../README.md)の「データの確度について」の表を参照。

## 3. 見つかった不具合と教訓（同じ轍を踏まないために）

2026-08-13のセッション中に発見・修正したバグを列挙する。多くはThree.js特有の癖なので、Web表示ロジックを触る際は要注意。

| 症状 | 原因 | 対処 |
|---|---|---|
| 一部の部屋だけ色が薄い/白く見える | 半透明オブジェクトの`depthWrite`がデフォルトで有効なため、重なった別の半透明レイヤーが下の色を隠す | 全ての半透明マテリアルに`depthWrite:false`を設定 |
| 部屋の輪郭線がチラつく/薄い | 隣接する2部屋が同じ境界線を別々に描画し、Z-fighting | 輪郭線マテリアルに`depthTest:false`を追加し、`renderOrder`だけで描画順を決定させる |
| 矩形とL字ポリゴンで色味が違って見える | `MeshStandardMaterial`は光源方向・法線で陰影が変わる。ポリゴン(ExtrudeGeometry)と矩形(BoxGeometry)で法線の向きが揃わないと陰影差が出る | `MeshBasicMaterial`（ライティング非依存）に変更 |
| 2F西面の窓がx=0（1F西端）に誤配置 | `face:'W'`の開口部は常に絶対西端(x=0)に固定する実装だった。2F自体の西壁はx=12.740 | 開口部データに`x`フィールドを追加し明示指定できるよう改修 |

| 片流れ屋根レイヤーをオンにすると、屋根が間取りの下に隠れて見える | 全ての半透明マテリアルで`depthWrite:false`にしているため、前後関係は実際のY座標ではなく`renderOrder`の数値だけで決まる。屋根メッシュ(`slopedRoofBox`)だけ`renderOrder`を設定し忘れていて既定値0のまま描画されていた（外皮=1、室内間仕切り=2、ドア/開口部=3より低い） | `slopedRoofBox`に`renderOrder`引数を追加し、屋根を4（他レイヤーより後＝手前）に設定（2026-08-14） |
| `Ryuka-Landscape-Designer`の`data/fixed-site-data.js`にも同じfl1/fl2の誤りがある | 同リポジトリのコメントに「基礎高0.500」と明記されており、`fl1`という変数名でありながら実際は基礎高を表す値として設計されていたと判明。当リポジトリのHTMLは元々ここからLEVELSをコピーしていたため、誤りごと引き継いでいた | 当リポジトリでは4章の通り立面図の実測値に修正済み。`Ryuka-Landscape-Designer`側は未修正（別リポジトリのため対象外）。今後同リポジトリの値を参照する際はfl1/fl2が基礎高基準である点に注意 |

| 窓・ドアの壁線スライドで、区画の継ぎ目（例：x=9.100）を一度越えると、越えた側からは元の区画側へドラッグで戻せなくなる「片道の罠」になっていた | `wallRangeForOpening()`が可動範囲を「現在位置が属するfootprint（求積図のゾーン区分）1個」だけから計算していたため、境界を越えて隣のfootprintに入った瞬間、次のドラッグではそちらのfootprintの範囲でクランプされ、越えた方向にしか動けなくなっていた。x=9.100は実際には1本の連続した壁（`1f-a1`〜`1f-a3`が同じ南辺z1=6.370を共有）で、区画分けは求積図上の都合でしかなかった | 現在位置のfootprintから、同じ辺(z0/z1)を共有し隙間なくつながっている区画をすべて合わせた範囲を返すよう修正（2026-08-15、施主の実操作で発覚）。**「1個のfootprintだけで範囲を決める」設計は、区画境界が実在の壁とは限らないこのデータでは常に境界付近で罠になりうる。今後この種の範囲計算をする際は、必ず隣接区画への連続性を確認すること** |
| 斜め框で部屋を分割した際、境界付近だけオレンジ色が濃く表示された | `buildRoomsApprox()`が「頂点4つ＝矩形」と決め打ちし、`polygon.length > 4`のときだけ実ポリゴン(`poly`)を使い、それ以外はバウンディングボックス(`boxWire`)で描画していた。斜め框で分割した2部屋はどちらも頂点4つの台形（矩形ではない）だったため、実形状ではなく外接する四角形で描画され、斜辺付近で2部屋のバウンディングボックスが重なった。半透明マテリアルは重なるほど濃く見えるため（3章の別バグと同じ原理）、境界付近だけ色が濃くなって見えた | 「頂点が4つかどうか」ではなく「全ての辺が軸に沿っているか(`isRectilinear()`)」で判定するよう修正（2026-08-15、施主の実機確認で発覚）。**矩形の判定を頂点数だけで行わないこと。斜めの辺を持つ部屋を今後も追加する可能性があるため、常に実形状で判定する** |
| 開口（アーチ、`operation:'open-arch'`）が、塗りつぶしを付けていたはずなのに平面図モードでも俯瞰モードでもほぼ見えなかった | `archOpeningMesh()`が、天端が円弧の完全に鉛直な板（厚みゼロのShapeGeometry）1枚だけを描画していた。他のドア・開口は`boxWire()`や`BoxGeometry`ベースで実際に厚み（0.06m）のある箱として描いているため、真上から見ても輪郭の分だけ面積が見えるが、この板は厚みが完全にゼロなので、真上から見ると輪郭線ごと一直線に潰れて消える。俯瞰モードでも、カメラの角度・板の向きによっては同様にほぼ視認できない角度になりうる | `open`と同じ矩形の枠線（厚みのある`BoxGeometry`のedges）を必ず重ねて描くよう修正し、板自体もピンクの塗りつぶしをやめて黒線のみに統一した（2026-08-16、施主指摘で発覚）。**厚みゼロの平板ジオメトリは、見る角度によって完全に不可視になりうる。開口・パネル系の要素は、最低限の視認性を保証するために厚みのある形状（箱の輪郭線など）を必ず一緒に描くこと**。ただしこの視認性用の枠線を、アーチ本体と同じ高さ（`d.height`）の箱にしたところ、アーチの立ち上がり（springHeight）より上の箱の角が、俯瞰モードでアーチの輪郭からはみ出して見える二次的な不具合を生んだ（施主が俯瞰スクリーンショットに赤丸で指摘）。**視認性確保だけが目的の補助ジオメトリは、本体の形状と競合しない最小限のサイズ（今回は床面近くの高さ0.05mの薄い箱）に留めること。厚みを持たせること自体は正しい判断でも、「どれだけの厚みが必要か」は本体の形状を踏まえて決める必要がある** |
| 内覧モードで、壁が塞がっているべき箇所とドアが開通しているべき箇所がランダムに入れ替わって見えた（「使い物にならない」レベルの不具合） | 壁の区間から壁厚・ドア幅ぶんを切り欠く`subtractRanges(ranges, cutFrom, cutTo)`が、`if(b > cutTo) out.push([Math.max(a,cutFrom), b]);`と、後半の切り出し開始点に`cutTo`ではなく`cutFrom`を使っていた（コピペミスと思われるオフバイワン）。区間`[0,10]`から`[3,7]`を引くと本来`[[0,3],[7,10]]`になるべきところ`[[0,3],[3,10]]`（合わせると`[0,10]`のまま何も削れていない）を返していた。この1関数が「ドアの位置で壁を切り欠く」処理と「隣接footprintの共有辺を除外して外壁だけを残す」処理の両方で使われていたため、影響はドア32件中24件（壁が塞がったまま）と、1階に実在しない「幽霊壁」が1本（本来ない場所の共有辺がキャンセルされず壁として残存）という、2種類の被害を同時に生んでいた | `Math.max(a,cutTo)`に修正（2026-08-16、施主指摘の「壁があったりなかったり」という報告を受けて調査し発覚）。**区間の引き算のような対称的な処理（前半・後半で似た式を2回書く）は、片方だけ変数を書き間違えても両方とも「それらしい」区間が返ってしまい、目視でもテストなしでも気づきにくい。今回のように影響範囲が広い共通関数（複数の別々の目的で使い回されている）ほど、単体テストで境界値（cutFromちょうど、cutToちょうど、範囲の内部、範囲外）を検証しておく価値が高い** |
| 上記のsubtractRanges修正後も、施主から「玄関ドアの外壁が透明で家の中まで見える箇所がまだ結構ある」と指摘があった。規則性は「壁がある場所とない場所が混在している」というだけで、施主自身にも原因の見当がつかなかった | ドアの位置で壁を切り欠く`cutGaps()`が、切り欠いた後の断片を`{orientation:s.orientation, at:s.at, from:a, to:b}`という新しいオブジェクトで再構築しており、元のセグメントが持っていた`thick`（壁厚）を引き継いでいなかった。`thick`が`undefined`になると、`resolveWalk()`の当たり判定は`PLAYER_RADIUS + undefined/2` = `NaN`になり比較が常に偽（すり抜け）、`boxWire()`の壁メッシュ生成も`Math.max(NaN, 0.02)`が`NaN`になりジオメトリが不正で描画されない。**ドアや窓の近くの壁だけが選択的に消える**という、まさに施主が観察した「規則性」の正体だった（一度も切り欠かれていない壁は無傷でthickが残るため、そこだけ正常に見えていた） | `{...s, from:a, to:b}`に変更し、元のプロパティ（`thick`含む）をすべて引き継ぐよう修正（2026-08-16）。**「一部のプロパティだけを明示的に指定してオブジェクトを再構築する」コードは、元のオブジェクトに後から追加されたプロパティ（今回で言う`thick`）を静かに失う。分割代入や個別フィールドの列挙ではなく、スプレッド構文で元のオブジェクトを基点にし、変更したいプロパティだけを上書きする方が安全**。またこのバグは`subtractRanges`のバグとは独立した別の不具合で、後から見つかったことからもわかる通り「1つ直しても関連箇所に別のバグが潜んでいないか」を疑う姿勢が要る |
| 内覧モードで、民泊LDKから見て壁の向こうにあるはずの階段（自宅1F）の輪郭線が透けて見えていた | 階段の3D段差の輪郭線マテリアル`stairEdgeMat`に、他の平面図線画用マテリアル（`approxEdge`等）から流用した`depthTest:false`が付いたままだった。3章の別項目（本表49行目）の通り、`depthTest:false`は元々「俯瞰・平面図モードでのみ使われる輪郭線を、renderOrderだけで前後関係を制御して常に手前に見せる」ための意図的な設計だが、これらの線画は`groups.approx1/approx2`等、内覧モードでは非表示になるグループに属している。ところが階段の3D実体(`groups_stairs`)だけは「俯瞰・平面図・内覧の全モードで常時sceneに存在させる」という別の設計（施主指摘により新設、4章参照）のため、depthTest無効の設定を素のまま持ち込むと、内覧モードでも手前の壁を無視して輪郭線だけが常に描画されてしまっていた | `stairEdgeMat`から`depthTest:false`を外し、通常の深度テスト（壁など手前の不透明物に隠れる）に戻した（2026-08-16、施主が民泊LDKからのスクリーンショットで指摘）。**`depthTest:false`は「常にそのモードでしか見えない前提のグループ」でのみ安全な設定であり、複数モードで共有される実体（今回の階段のように、俯瞰・平面図・内覧すべてに存在するジオメトリ）に同じマテリアルを流用する際は、そのモードごとの前提（内覧モードでは壁が本当に視界を遮る必要がある）が崩れていないか確認すること** |

同じセッション内で、施主から「`door-window-catalog.json`でドアと窓のカタログを1つにまとめている意味はあるか。furnitureのように、ドアで一式・窓で一式という形にファイル構成を分けた方が管理しやすいのでは」という質問を受けた。

検討の結果、**「分ける軸が2つあり、それぞれ別の理由で決まる」**という整理で合意した。

- **カタログ（型のライブラリ）は種類（ドア/窓）で分ける**：`data/door-catalog.json`・`data/window-catalog.json`に分割。理由は、施工会社の建具表・サッシ表が実務上も別表であることが多く、ドアと窓は「共通スキーマ」というだけで本質的には別物（ドアは開き勝手が主題、窓は開閉可否が主題）だったため。当初「furniture-catalog.jsonがcategoryフィールド1つで済ませている」ことを理由に1ファイルにまとめていたが、これは技術都合寄りの判断だったと振り返って認めた
- **配置インスタンス（`openings.json`）は位置決めの仕組み（外周/内部）で分けたまま維持する**：exterior側の窓・ドアは`face`+`offset`という位置決めの仕組みが共通で、壁の開口切り欠き処理（`build_exterior_walls`等）や将来の同一壁上の重なりチェックで窓・ドアを同時に扱う必要があるため、無理に分けるとビルドスクリプト側の複雑さが増すだけと判断した

- **ドアの開閉演出**：`addWalkDoorLeaves()`を新設し、開き戸・両開き戸・引き戸それぞれについて、内覧モード専用の厚みのある扉パネル（`walkGroup`に常設、平面図側の`groups.doors1/2`とは別レイヤー）を閉位置で配置した。開き戸は蝶番位置を原点にしたグループを`rotation.y`で回転させる方式にし、閉角度・開角度は沿い方向／直交方向の単位ベクトルから`Math.atan2()`で求めた（`boxWireRotated()`と同じ規約の流用）。実装中、蝶番側・開く向きの組み合わせによっては閉角度・開角度の差が180度を超え、素直に線形補間すると90度で足りるところを270度の遠回りで回転してしまうケースがあることに気づき、`shortAngleLerp()`（最短経路で角度を補間するヘルパー）を追加して対処した。折れ戸・両開き折れ戸は、実際の2枚折れ機構までは再現せず開き戸・両開き戸と同じ回転運動で簡略化した（平面図側の専用のハの字表現とは別の割り切り）。毎フレーム、プレイヤーとの距離が1.8m以内かどうかで開閉度をなめらかにイージングする
- **家具の当たり判定**：家具の回転が0/90/180/270度のみという既存の前提（`data/furniture.json`のnote）により、回転後の外形は必ず軸に沿った矩形になることを利用し、各家具の4辺を壁と同じ「線分＋当たり判定半径」の当たり判定にそのまま追加した（新しい当たり判定ロジックを別に書く必要がなかった）
- 両方ともPlaywrightで検証：ドアはプレイヤーとの距離をコード上で操作し、近づくと開閉度が0→1へ、離れると1→0へなめらかに戻ることを確認。家具はソファに向かって歩かせ、「ソファの実効境界＋プレイヤー半径」ちょうどの距離（計算値と実測値が完全一致）で止まることを確認した。あわせて、建物内をランダムウォークさせて完全に身動きが取れなくなる（壁と家具に四方を塞がれる）ケースがないことも簡易的に確認した

**第10弾：内覧モードの残存バグ2件の修正、三人称視点の追加**：コミット後、施主自身の実機確認から2つの続報があった。

- 1つ目：「玄関ドアの外壁がまだ透明な箇所がある」という追加指摘。壁の区間からドア幅を切り欠く`cutGaps()`が、切り欠いた後の断片を明示フィールドの列挙で再構築しており、元のセグメントが持っていた`thick`（壁厚）を引き継いでいなかったことが原因と判明した（3章の教訓の表参照）。`thick`が`undefined`になると当たり判定はNaNで常にすり抜け、壁メッシュもNaNジオメトリで描画されない。ドアや窓に一度でも切り欠かれた壁だけが選択的に消えるという、施主が指摘した「規則性」の正体はこれだった。スプレッド構文で元のプロパティを全て引き継ぐよう修正した。
- 2つ目：民泊LDKからのスクリーンショット付きで「壁の向こうにある自宅の廻り階段が透けて見える」という指摘。階段の3D段差の輪郭線マテリアル`stairEdgeMat`に、他の平面図線画用マテリアルから流用した`depthTest:false`がそのまま残っていたことが原因だった。この設定自体は元々「俯瞰・平面図モードでのみ使う輪郭線を`renderOrder`だけで前後関係を制御して常に手前に見せる」という意図的なものだが、`groups_stairs`（階段の3D実体）は俯瞰・平面図・内覧の全モードで常時sceneに存在する特別な存在のため、depthTest無効のまま内覧モードに持ち込むと、手前の壁を無視して輪郭線が常に描画されてしまっていた。`depthTest:false`を外して修正した。
- 続けて施主から「三人称視点も作りたい。マインクラフトのように170cmの人物を歩かせ、三人称視点から広さ・狭さを把握したい」という新規リクエストがあった。実装は以下の方針で行った。
  - **キャラクターモデル**：日本人成人男性の平均身長170cmを想定した簡易ブロック体型（脚0.85m＋胴0.55m＋頭0.30m）を`BoxGeometry`の組み合わせで新設（`walkCharacterGroup`）。局所座標は足元をy=0、正面を+Z向きとして組み、`group.rotation.y`にそのまま`walkYaw`を渡せるようにした（既存の`boxWireRotated()`・扉の開閉演出と同じ回転規約の踏襲）。あくまでスケールの目安であり、体型・服装の再現性は求めていない
  - **カメラ**：一人称と同じ`(fx,fy,fz)`のforwardベクトルを再利用し、注視点（キャラの頭部付近、床から1.5m）からその逆方向に距離3.2mだけ離れた位置をカメラの理想位置とした。`walkPitch`で見上げ・見下ろしすると、その分カメラも弧を描いて上下する。一人称・三人称は`walkView`という状態変数で切り替え、内覧モードのHUDボタンまたは`V`キーでトグルする（`toggleWalkView()`）
  - **壁・家具へのめり込み防止**：既存の家具当たり判定（`resolveWalk()`内にクロージャとして閉じていた`blockedBy()`）を`segListBlocked()`という独立関数に切り出し、プレイヤーの歩行判定（`resolveWalk()`）と三人称カメラの両方から再利用できるようにした。カメラは注視点から理想位置へ向けて24分割の短いステップで進めながら衝突判定し、最初にぶつかった手前で距離を打ち切る（Playwrightで、家具の近くでは数十cmまで、開けた場所では設定上限の3.2mまで、狭い部屋の中央でも1m未満まで、と状況に応じて距離が変わることを確認した）。この家は部屋の中央でも壁・家具まで1m未満のことが多く、三人称カメラは多くの場面でかなり近距離に寄ることになるが、これは「壁に対してキャラクターの体がどれくらいの余白で収まるか」が一目でわかるという、施主が三人称視点に求めた目的そのものに合致する挙動だと判断し、そのままにした
  - 検証時、家具の近くを最初のテスト地点に選んだところカメラがほぼゼロ距離まで詰まり、原因調査に時間を使った。実際には家具のすぐ脇（数cmしか離れていない）をテスト地点に選んでしまっていたためで、実装のバグではなかった（このセッション中に既に2回発生していた「衝突判定の検証用に選んだ座標が、判定対象のすぐそば・境界上だった」という同じ種類のテスト構築ミスの3回目）

続けて施主から、内覧モードについてさらに2点の指摘があった：「開口（アーチ）がアーチ開口になっていない（通常開口と同じく単純に壁を取り除いただけ）」「ドアと同じように窓データも認識させ、内覧でも窓がわかるようにしてほしい」。

- **窓が内覧モードに存在しない問題**：調査したところ、壁の当たり判定・壁メッシュ生成のどちらの元データにもなる`doorGapsForLevel()`が、`OPENINGS`のうち`category==='door'`のものしか壁の切り欠きに使っていないことが分かった。窓（`category==='window'`）は最初から一切ここに含まれておらず、内覧モードでは「窓のある位置もただの壁」として描かれていた（透けて見えるどころか、そもそも窓の存在を示すものが何もなかった）。ドアと違って窓は床から天井までではなく`sill`（下端高さ）〜`sill+h`の帯だけを開けたいので、単純にdoorGapsと同じ全高カットの対象に加えるわけにはいかない。既存の`rectMinusRect()`（2F床・内覧モードの天井から階段の吹き抜け穴を切り欠くのに使っている汎用の矩形引き算関数）を、壁を「沿い方向×高さ方向」の2D矩形とみなすことで転用し、窓の帯を切り欠いた残りを壁として描画、窓の範囲には半透明のガラス面（`walkWindowMat`）を追加する方式にした。窓は当たり判定用の`wallSegmentsByLevel`には含めない（＝壁のまま）ことで、「窓から出入りできてしまう」という新たな不具合を生まないようにした
- **アーチ開口が四角い開口に見える問題**：`doorGapsForLevel()`はアーチ開口（`operation:'open-arch'`）も他のドアと同じ「壁を全高で切り欠く」対象に含めていた（当たり判定としてはこれで正しい。人が通れる範囲は結局アーチの下の矩形部分とほぼ同じなので、弧の形まで衝突判定する意味がない）。問題は見た目だけで、壁メッシュ生成側では単に「窓と同じくアーチの範囲を全高で穴を開けたまま」なので、天井まで抜けた四角い開口に見えていた。修正は、平面図モードで使っている`archOpeningMesh()`（弧の形を`THREE.Shape`で描く関数）の式をそのまま流用し、弧の**外側**（迫り持ち＝スパンドレル部分）を壁と同じ色で追加描画するという発想にした。弧は左右の springHeight 地点から頂点（`springHeight+archRise`）へ滑らかに盛り上がる形なので、迫り持ちの領域（弧の上側かつ矩形の内側）は左右それぞれが頂点で接する2つの三日月形になる。1つのShapeで表現しようとすると頂点で自己接触する退化した形になり三角形分割が不安定になりかねないため、`archSpandrelShapes()`は左右を別々の単純な閉多角形として返すようにした。あわせて、ドアの高さ（アーチの頂点の高さ）が天井高より低い分（この家では0.3mだけ）は、通常の垂れ壁と同じ扱いで追加した
- 両方とも、実際のデータ（唯一存在するアーチ開口`door-006`＝ヌックのアーチ開口、および複数の窓）でPlaywrightのスクリーンショットを撮って確認した。検証の最初の2回は、カメラの向き（`yaw`）を意図と逆に設定してしまい（`forward=(sin(yaw),cos(yaw))`という規約に対し、南を向かせたいのに北を向く`yaw`を指定する、といった単純な符号の勘違い）、対象が画面に映らず「見えない」という誤った結果になった。前回セッションで方角を勘違いした際と同種のミスであり、内覧モードのデバッグでは「まず`yaw`の向きが意図通りか」を機械的に見直す必要があると再確認した

その後、施主から三人称視点そのものについて「動かすと、障害物との位置関係かで視点カメラが寄ったり引いたりする。うっとうしいので、引き気味の視点から一定にしてほしい」という指摘があった。前回の実装では、壁・家具に応じてカメラ距離を自動調整すること自体を「壁に対してキャラクターの体がどれくらいの余白で収まるか一目でわかる、狙い通りの挙動」と判断していたが、実際に施主が操作した結果は「歩くたびにズームイン/アウトを繰り返して落ち着かない」という、狙いとは違う体験だった。距離の自動調整ロジック（`pointBlocked()`によるレイマーチ衝突判定）を丸ごと削除し、カメラ距離を常に`THIRD_PERSON_DISTANCE`で固定する方式に変更した。壁にめり込む場合はそのまま許容する（近距離で壁の裏側の面が大写しになることはあるが、通行や当たり判定には影響しない）。**「衝突を避けて距離を自動調整する」という設計は、意図としては合理的でも、頻繁に距離が変わること自体が体験として気持ち悪くなりうる。実際に触った施主のフィードバックがない限り、「これは正しい動作のはず」という自分の判断だけで確定させないこと**。あわせて、固定距離（当初3.2m）についても「もう少し近くても大丈夫」と1.5m詰める指示があり、1.7mに変更した

続けて、内覧モード中に画面の右上に平面図のミニマップを置き、プレイヤーの位置・向きを表示し、クリックでその場所へワープできるようにしてほしいという要望があった。3D描画（Three.js）とは完全に独立した、`<canvas>`＋`CanvasRenderingContext2D`による単純な2D描画で実装した（Three.jsのオルソカメラで別ビューポートに描画する方法も検討したが、既存のシングルレンダラー構成に複数ビューポート・シザーテストを持ち込むよりも、素直な2D描画の方が実装・保守ともに単純だと判断した）。壁の線は、当たり判定・壁メッシュ生成と同じ`wallSegmentsByLevel`をそのまま流用したため、ミニマップ上の壁と実際に歩ける壁が食い違う心配がない（別データソースを持つと、片方だけ更新し忘れるという、このセッションの前半で扱った「rooms/walls二重管理」と同種の問題を再び生みかねないため）。座標変換は建物ローカル座標⇔キャンバスピクセル座標の単純な線形写像（`minimapTransform()`）で、クリック時はその逆変換で建物座標を求め、`segListBlocked()`（三人称カメラの旧衝突判定から流用した、プレイヤーの当たり判定と共通の関数）で壁の中でないことを確認してから`walkPos`を直接書き換えるだけの、シンプルな実装で足りた。

ミニマップの実装・確認とは無関係に、施主から新たに「自宅LDKから東の廊下へ抜けようとすると、急に2階にワープする」というバグ報告があった（ミニマップは操作していないと明言されており、別の不具合だと最初から見当がついた）。調査の結果、階段に乗っているかどうかを判定する`stairProgressAt()`が、経路（折れ線）との最短距離だけで「乗っている/いない」を決めており、壁の有無を一切考慮していないことが原因と判明した。階段の経路の終端（パントリーの真上を通る直進部分、x=15.016）は、東の廊下(room-1f-13)の南西角(15.471,1.82)からわずか0.455mしか離れておらず、判定半径（`width/2+STAIR_CORRIDOR_MARGIN`=0.805m）に楽々収まってしまう。実際には両者の間に壁が1枚あり、廊下を歩いている人は物理的に階段に近づけないのだが、`stairProgressAt()`はそれを知らない。修正は、階段の経路が本来収まっているはずの矩形（`stair.opening`。もともと2F床に開ける吹き抜け穴として定義されているデータだが、1F側の階段室の外接範囲としても正確に使える）の外なら、距離に関わらず即座に対象外とする足切りを先頭に追加した。**距離ベースの近接判定（「半径〇〇m以内なら対象」という発想）は、対象が壁で仕切られた別の部屋のすぐそばにある場合、壁を無視して誤検知しうる。今回のように経路の一部が別の部屋のすぐそばを通る設計（階段の踊り場がパントリーの真上に隣接する等）では特に起こりやすく、机上のデータだけでなく実際に歩いて動作確認する価値が高い**。修正後、階段の経路をなぞって実際に歩くテスト（`walkLevel`を`updateWalkMovement()`と同じロジックで動的に切り替えながら`t`が0→1まで連続して進むかを確認）で、正常な昇降が壊れていないことも確認した。

続けて、施主から「洗面と廊下をつなぐ部分に開口ドアを設けてください。前回つけ忘れました」という指摘があった。room-1f-13（廊下）とroom-1f-15（洗面(東)）の共有区間（x=17.291、z:2.73-3.64）を確認すると、確かにこの区間だけ`interior-doors.json`にエントリがなかった。ちょうど区間の長さが0.91m＝`door-open`カタログの標準幅と一致していたため、`widthOverride`なしでそのまま追加できた（`door-031`）。追加後、`resolveWalk()`をコード上でシミュレートして実際に廊下側から洗面側まで歩けることを確認した。

さらに施主から「片開き折れ戸、両開き折れ戸の内覧モードの開き方が、通常の開き戸・両開き戸と同じモーションになっている。折れ戸特有の物理があるので専用のモーションを作ってほしい」という指摘があった。この簡略化（開き戸と同じ回転運動で近似）は、前々回のドア演出実装時に「折れ戸・両開き折れ戸は、内覧モードでは実際の2枚折れの機構までは再現せず」と明示的にドキュメント化した上での意図的な妥協点だったが、実際に触った施主からは簡略化では不十分という評価だった。実装は、平面図の折れ戸記号（`drawFoldLeaf()`）の幾何（蝶番A・折れ点B・自由端Cが正三角形A-B=B-C=A-C=w/2をなす）を出発点に、実際の折れ戸の拘束条件（自由端Cは常に壁面の延長線上をスライドする）を満たす回転の組み合わせを逆算した。パネル1（A-B）をヒンジAまわりに角度θで回転させ、パネル2（B-C）をパネル1に対して常に-2θ（パネル1に対して逆向きに2倍）回転させると、幾何学的にCは常に壁面の延長線上に留まったままBだけが張り出す、という関係が成り立つ（二等辺三角形の対称性による）。θ=0（閉、パネル1・2が一直線に並び全開口幅を塞ぐ）からθ=60°（平面図の記号と同じ開き角度）まで、既存の`t`（0=閉,1=開）でイージングする。実装後、Three.jsの`localToWorld()`で自由端の実際のワールド座標を計算し、閉状態でC=蝶番+全開口幅（平面が塞がる）、開状態でC=蝶番+開口幅の半分（＝平面図記号のC地点と一致）になることを、片開き・両開きの両方で数値的に検証した（想定値と計算値が小数点以下まで完全一致）。**平面図で先に確立された静的な記号のジオメトリ（正三角形）は、そこから逆算すれば3Dの動的な機構（回転の拘束関係）を導出できるヒントになっていた。「平面図の記号を真似た近似」で済ませず、その記号が表している物理的な拘束条件そのものを考えることで、近似ではなく正確な再現に到達できた**。

続けて施主から、2Fの平面図スクリーンショットに赤線を引いて「廻り階段のところ、赤い線を引いた位置に対して1.5mぐらいの腰壁を作れますか。いまのままだと2階から1階に飛び降りれてしまうような状態」という指摘があった。調べると、2F階段室（room-2f-02、`stair.opening`と同一形状の吹き抜け）の南辺は、`door-030`（階段(2F)⟷廊下(2F)）が全幅(1.819m)を壁のない開口にしているため、そのまま2Fの廊下から吹き抜けへ踏み込める状態になっていた。ただし全幅を塞ぐと、実際に階段へ出入りする通路まで塞いでしまう。階段経路のデータ（`stair.segments`・`hiddenBelow`）を読み解くと、南辺のうち東側半分（x:14.561-15.471）は階段の最後の直進部分＝上端の着地部分の真上にあたり、西側半分（x:13.651-14.561）は廻り部分の真上でまだ2F床がない吹き抜けだと判断できた。西側半分だけに腰壁を追加すれば、施主の指摘する転落経路を塞ぎつつ、階段への出入りは開放したままにできる。

実装にあたり、`rooms`の隣接関係から壁を自動導出する現行アーキテクチャでは、腰壁のような「部屋の境界ではない、吹き抜けの縁に立てる安全柵」を表現する仕組みがそもそも存在しないことに気づいた。既存の`specialWalls`（防音壁、`house.specialWalls[0]`を単一のグローバル定数`SOUND_WALL`として直接コード中で参照する、一点もの前提の実装）を見つけ、同じ「rooms由来ではない特別な壁」という位置づけの前例として踏襲することにした。ただし`SOUND_WALL`の単一オブジェクト決め打ちの実装をそのままコピーすると、将来また同種の壁が必要になったときに三つ目のハック実装を重ねることになる。今回は最初から配列（`guardWalls`）として設計し、`GUARD_WALLS`定数・`buildGuardWalls()`をひとつの一般的な仕組みとして用意した。当たり判定は、既存の`wallSegmentsByLevel`の構築ロジック（`resolveWalk()`・`segListBlocked()`は`thick`しか見ない）にそのまま乗せられたが、内覧モードの見た目（壁メッシュ生成ループ）は天井の高さ(`CEIL_H`)を決め打ちしていたため、そのままでは腰壁のつもりが天井までの壁になってしまう（吹き抜けが完全に隠れてしまい、施主が求めた「腰の高さの手すり」にならない）。セグメントに`guardHeight`という追加フィールドを持たせ、ループの先頭で分岐させることで対応した。**「収まりの良い前例（SOUND_WALLのような一点ものの特別扱い）を見つけたときほど、そのまま複製するのではなく、次に同じ種類の要素が増えても破綻しない形に一段階引き上げてから使うと、あとで三つ目のハックを重ねずに済む**。実装後、Playwrightで平面図の該当区間を拡大表示して壁の輪郭線が実際に描画されていることを確認し、内覧モードでは腰壁の区間で衝突判定によりプレイヤーが止まること・階段への出入り側（開放した東側半分）は今まで通り通行できることの両方を、`resolveWalk()`のシミュレーションで数値的に検証した。

一連の内覧モード改善（`feature/walk-mode-walls`ブランチ、10コミット）がPR #8としてマージされたのを受けて、`main`から新しく`feature/sloped-ceiling`ブランチを切り、次の施主リクエストに着手した：「民泊LDKと自宅LDKの部分、かつ片流れ屋根がかかっている範囲は、天井の高さを片流れの形に合わせてほしい」。

まず実装方針だけをまとめて提示した（実装はまだしない、という施主の指示）。`data/house.json`の`footprints`（求積図のゾーン）・`roofs`（片流れ屋根、`roof-a1`/`roof-a2`）・`rooms`のポリゴンを突き合わせ、対象になりうる部屋（民泊LDK・自宅LDK）と、勾配天井にできる範囲（片流れ屋根がかかる部分のみ。自宅LDKは東側1/3が2階の直下のため対象外＝フラットなまま段差になる）を特定した。天井高を実際に計算すると、屋根裏面そのままで床から約3.0〜3.65m（現状の一律2.4mから大幅に上がる）になることも分かった。あわせて、自宅LDK南面の掃き出し窓（`op-010`）の上端(2.45m)が現状の天井(2.4m)を既に突き抜けているというデータ上の傍証も見つけ、勾配天井が実際の設計意図である可能性を補強する材料として提示した。方針では「天井を上げるだけでなく、壁の高さも屋根なりに伸ばす（さもないと壁の上に隙間ができて隣室が丸見えになる）」という、当初の施主の依頼文言（天井の話）からは明示されていない副次的な要件を自分から指摘した。**施主から明示的に聞かれていない部分でも、要求を素直に実装した結果どうなるかを想像すると副作用が見えることがある。それを先回りして伝えることで、後から「壁との取り合いも考えてほしかった」と手戻りになるのを防げる**。方針提示に対し、施主から3点の判断（屋根裏面そのままではなく見込みを引く／ヌックは対象外／2階直下でフラットに戻る段差はそのままでよい）をもらい、実装に進む前にPRのマージを挟んでから着手する運びになった。

実装は、まず`data/house.json`の対象部屋に`ceiling:"sloped"`という最小限のフラグだけを追加し、残りは全部既存データから導出する設計にした（「どの部屋を勾配天井にするか」は施主の判断が必要だが、「どの屋根がかかるか」「どこでフラットに戻るか」「壁がどれだけ高くなるか」はすべて既存の`roofs`/`footprints`/`rooms`から機械的に求まるはずで、手で入力すると部屋の形が変わった時にズレる）。最大の技術的な難所は、対象の2部屋がどちらも矩形ではなくL字・階段状のポリゴンだったこと（民泊LDKは張り出し部を含むL字、自宅LDKは北端が3段階の階段状）。単純な外接矩形で扱うと、実際には部屋の外にある領域まで「勾配天井の対象」と誤判定しかねない。z方向の走査線で矩形群に分解する標準的なアルゴリズム（`decomposeRectilinearPolygon()`）を実装し、各矩形を屋根のfootprintと交差判定してsloped/flatに分けた。

壁の高さ調整は、当初の想定より場合分けが多かった。z一定の壁（H向き）は屋根の勾配式もzに依存するだけなので区間内では高さが変わらないが、壁の途中でx方向に「屋根がかかる／かからない」の境界（自宅LDKのx=12.74）をまたぐことがあり、そこだけ区間分割して段差にする必要があった。x一定の壁（V向き）は逆に「屋根がかかるか」自体は壁の全長で変わらないが、高さそのものがzの一次式で連続的に変わるため、上端が傾いた台形のパネルが必要になった（民泊-自宅の防音壁もこの一種で、たまたま両側とも勾配天井の部屋なので天井なりに傾く対象に含まれた）。傾いた台形パネルは、既存のアーチ開口の迫り持ち（`archSpandrelShapes()`）と同じ「ローカル平面のShapeをZ方向に押し出し、position+rotation.yで配置する」手法を流用したが、シェイプの座標を実際のz座標そのまま（例えば2.73や6.37）で組んだところ、`mesh.rotation.y`による回転が原点(0,0,0)を中心に起きるため、形が原点から遠く離れた位置に組まれた図形は回転で全く違う場所に飛んでいってしまう、という間違いに気づいた。シェイプ座標を壁の始点(`from`)からの相対値に組み直し、位置決めのtoScene()呼び出し側で始点の実座標を渡すよう修正した。**回転を伴うジオメトリを組むときは、シェイプ自体の座標系の原点と、実際に回転の中心にしたい点を一致させること。回転前提のジオメトリに実世界の絶対座標をそのまま使うと、回転後に全く違う位置へ飛んでいく**（三人称キャラクターやアーチのスパンドレルなど、このリポジトリで既に確立していたはずのパターンだが、絶対座標を使った新しいケースで改めて踏み抜きかけた）。

検証は、`slopedCeilingHeightAt()`を直接呼び出して天井高が期待通りの値（部屋の外にあたる点ではCEIL_H、部屋の中では屋根なりの値）になっているかの数値チェック、傾いたパネルの実際の頂点をワールド座標に変換して南北の高さが正しく異なっている（＝本当に傾いている、単に高い位置でフラットなだけではない）ことの確認、H向きの壁がx=12.74で正しく段差になっているかの区間ごとの数値チェック、既存の壁の当たり判定（衝突は2D、高さと無関係なので影響を受けないはず）に回帰がないことの確認、俯瞰・平面図モード（今回は意図的に未対応）でエラーが出ていないことの確認、という5段階で行った。俯瞰・平面図モードの部屋ボックス（`ROOMS_APPROX`）とBlenderへの反映は、施主に伝えていた通り今回のスコープ外として残した。

実装完了を報告したところ、施主から2枚のスクリーンショットとともに「①自宅LDKの片流れとフラット天井の境目が抜けて2Fが見えてしまっています。②その逆、自宅LDKの民泊との境界の壁をみると、こちらは境界壁がおかしくなっています。ヌックを囲う壁も変になってしまっています」という指摘が届いた。「抽象的な指摘しかできませんが、どう修正すればいいか伝わりますか」と添えられていたが、スクリーンショットと、それまでに自分で組んだデータ構造（`SLOPED_CEILING_PIECES`の区画分解、壁の高さ計算のロジック）を照らし合わせることで、伝わったと判断し、そのまま調査に進んだ。

まず②から調べた。防音壁（x=7.28）の高さ計算を数値で追うと、壁の北端(z=0.91)から南端(z=6.37)まで、「本当は」z=2.73あたりまでフラット(CEIL_H)で、そこから先だけ勾配天井の高さに向かって連続的に上がっていくべきところ、実装（`heightEndsForVWall()`）は両端の2点だけを求めてその間を単純に直線で結んでいた。壁の一部だけが勾配天井の部屋に接し、残りは接しない（防音壁の北側はヌック等の非対象の部屋に接している）という、壁が複数の「区画」をまたぐケースを想定していなかったための誤りだった。この過程で、傾いたパネルを描く`slopedTopWallPanel()`にも別のバグが見つかった。実装時に「シェイプの高さ方向の座標は`topA-baseY`（絶対座標から基準を引いた相対値）にする」と決めていたが、実際に呼び出している側（`heightEndsForVWall()`の戻り値）は既にfloorからの相対高さで渡していたため、二重にbaseYを差し引いてしまい、壁の上端が実際より0.707m（`LEVELS.fl1`とちょうど一致）低い位置に描画されていた。前回の検証で「北端2.4・南端3.4985」という数値を見て「北が低く南が高い、傾いている」ことだけ確認して次に進んでしまったが、実際にはこの2つの数値自体が両方とも0.707mぶん低い、絶対座標としては誤った値だったことに気づいていなかった。**検証で数値を見るときは、「値の大小関係が期待通りか」だけでなく「その値が本来あるべき絶対的な基準（この場合は建物の各階の床の高さ）と一致しているか」までチェックする必要がある。前者だけの確認は、系統的なオフセット誤差（今回のような二重減算）を見逃す**。

①（自宅LDKのx=12.74の天井の穴）は、そもそも実装時に想定していなかったケースだった。同じ部屋の中で勾配区画とフラット区画が壁を挟まずに接する境界は、天井の高さが不連続に変わるのに、それを塞ぐ壁もジオメトリも存在しない。方針をまとめた段階で「フラットに戻る箇所は素直に段差でOK」という施主の了承を得ていたが、それは「間仕切り壁のような区切りがあるものとして段差にする」という意味であり、「区切りが何もない場所に穴が開く」ことまでは想定していなかった、という認識のズレがあった。**方針の合意を取る際、「段差でOK」のような一言の了承が実際にはどんな絵になるかを、自分の中で具体的にイメージ（この場合は3D空間でどう見えるか）してから実装に進むべきだった。抽象的な合意と具体的な実装結果の間にギャップが生まれやすいのは、まさにこういう箇所である**。加えて、ヌック⟷LDKのアーチ開口の「弧の頂点から天井までの垂れ壁」も同じ理由（`CEIL_H`決め打ち）で天井まで届いておらず、②の「ヌックを囲う壁も変」という指摘の実体はこれだった。壁の高さ計算のバグ修正だけでは直らず、アーチ専用の垂れ壁ロジック（`addWalkArchInfill()`）にも同じ「区間分割で正しい高さを求める」処理を横展開する必要があった。

3つとも修正し、施主の指摘した2箇所（自宅LDKのx=12.74境界、ヌックのアーチ）をPlaywrightで再現して、修正前は実際に隙間や不自然な壁が見えること・修正後はそれが解消されることをスクリーンショットで確認した。
