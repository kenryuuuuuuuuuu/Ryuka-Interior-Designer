# 背景・経緯（なぜこうなっているか）

このドキュメントは、プロジェクトの目的・データの作り方・過去に見つけた落とし穴を記録する。**新しくこのリポジトリを開くエージェントは、作業を始める前にこのファイルを読むこと。** 技術的な仕組み（正本・変更手順）は [ARCHITECTURE.md](ARCHITECTURE.md)、現在の進捗・未解決事項は [STATUS.md](STATUS.md) を参照。

## 1. このプロジェクトの目的（なぜこれを作っているか）

施主が2027年4月の竣工を予定している新築住宅（主居＋民泊棟の二世帯構成）の内装を、着工前に検証・意思決定するためのデジタルツイン。最終的な狙いは3つ。

1. **寸法・間取りの精度を上げること。** 施工会社の実施図面はCAD原本ではなくスキャンPDF/画像しかない。断面図もない（天井高が図面から読み取れない）。この白模型は、複数の参考資料を突き合わせて壁位置の矛盾を洗い出す検証ツールとして機能している
2. **施工会社への要望を視覚的に伝えること。** 平面図の口頭説明より、3Dモデルの方が伝わる
3. **将来的な意思決定の土台。** 家具配置・コンセント/照明位置・内装の質感検討を、この骨格の上に積み上げていく

**Three.js vs Blenderの位置づけ**：Three.jsは「寸法検証・骨格確認」に強く、実際にその通り機能した。一方「本物のような質感」（施主が当初イメージしていたゴール）は、Blenderの方が労力対効果で有利という評価を、2026-08-13のセッション中に伝えている。現時点でどちらに倒すかは未確定（[STATUS.md](STATUS.md) の未解決事項を参照）。

## 2. データの作り方（なぜこの数値なのか）

**ここが一番失われやすい文脈なので、必ず読むこと。**

### 2.1 情報源の優先順位

1. 施工会社の実施図面（Ver5、配置図・求積図・平面図・立面図の4葉。断面図はない）
2. `Ryuka-Landscape-Designer`リポジトリ（外観モデル、外皮の階高・軒高が実施図面と検算済みで確定）
3. マイホームクラウド（間取り作成サービス）の間取り画像。**面積・寸法線は信頼できるが、天井高・床高は物理的に矛盾する値を含んでおり、一切使用していない**
4. 上記から読み取れない部分は、910mmグリッド（尺モジュール）を前提に、面積からの逆算や画像のピクセル解析で補完

**PDF原本の所在**：上記1の実施図面PDF（`渡辺拳竜様邸新築工事.pdf`、Ver5・全4葉）は`docs/`に置いてあるが、施主の氏名・住所・電話番号を含むため`.gitignore`で除外しており、GitHub上には存在しない。ローカルのファイルシステムには残っているので、新しいエージェントは`docs/`配下を直接確認すること。この環境には`pdftoppm`（poppler-utils）が入っていないため、`pip install pymupdf`でPDFページをPNG化して読む方式を使った。

### 2.2 手法：画像のピクセル解析

CAD原本がないため、施主がマイホームクラウドの画面やこの白模型のスクリーンショットに赤線・青線を描き込み、それを都度ピクセル単位で解析して実寸に変換する、という作業を数十回繰り返して座標を確定した。

**技術的な教訓**：

- **キャリブレーションは離れた2点を基準にする。** 近接した2点（間隔0.9m程度）で比率を出すと、数ピクセルの誤差が大きく増幅される。過去に一度、この理由で壁位置を誤って「訂正」し、さらにそれを再訂正するという手戻りが発生した
- **赤/マゼンタ/水色などの色は、既存の描画要素（ドア=マゼンタ、窓=水色）と被ると誤認識しやすい。** ユーザーの手描き線は「純色（例: R<80,G<130,B>180）」、モデルの描画要素は半透明のブレンド色になることが多く、RGB値で判別可能
- **求積図の外形区分（A1〜A4ゾーン）と、実際の部屋割りは一致しない。** 例えば「LDK」は外形ゾーンをまたいで存在し、北側の壁が3段階（z=2.730→2.275→1.820）の階段状になっている実例がある

### 2.3 確度（status / conf）の運用

`高`/`中`/`低`（JSON側では`verified`/`derived`/`estimated`）の3段階で運用している。定義は[README.md](../README.md)の「データの確度について」の表を参照。

## 3. 見つかった不具合と教訓（同じ轍を踏まないために）

2026-08-13のセッション中に発見・修正したバグを列挙する。多くはThree.js特有の癖なので、Web表示ロジックを触る際は要注意。

| 症状 | 原因 | 対処 |
|---|---|---|
| 一部の部屋だけ色が薄い/白く見える | 半透明オブジェクトの`depthWrite`がデフォルトで有効なため、重なった別の半透明レイヤーが下の色を隠す | 全ての半透明マテリアルに`depthWrite:false`を設定 |
| 部屋の輪郭線がチラつく/薄い | 隣接する2部屋が同じ境界線を別々に描画し、Z-fighting | 輪郭線マテリアルに`depthTest:false`を追加し、`renderOrder`だけで描画順を決定させる |
| 矩形とL字ポリゴンで色味が違って見える | `MeshStandardMaterial`は光源方向・法線で陰影が変わる。ポリゴン(ExtrudeGeometry)と矩形(BoxGeometry)で法線の向きが揃わないと陰影差が出る | `MeshBasicMaterial`（ライティング非依存）に変更 |
| 2F西面の窓がx=0（1F西端）に誤配置 | `face:'W'`の開口部は常に絶対西端(x=0)に固定する実装だった。2F自体の西壁はx=12.740 | 開口部データに`x`フィールドを追加し明示指定できるよう改修 |
| ドアマーカーが壁からわずかにはみ出す | 部屋の境界ぎりぎりにドアを配置すると、数cmの計算誤差で越境する | ドアは壁の両端から余裕（0.05m以上）を持たせて配置。`tests/validate_house.py`に「全ドアが対応する壁の範囲内に収まっているか」の機械チェックを追加済み |
| 2つの窓が繋がって1本の長い窓に見える | 同じ壁(x=12.740)上に配置した2つの窓のz範囲が一部重複していた | 個別の窓のz範囲が重ならないことを確認してから配置する |
| rooms→walls変換で、複数ゾーンにまたがる壁が外壁として除外されない | 「壁の区間全体が1つのfootprintに収まるか」で判定すると、2つの隣接footprintにまたがる外壁を見逃す | 区間の「引き算」方式（該当座標の外皮区間を全て集めてから差し引く）に変更 |
| `house.json`の1F/2F床レベル(fl1/fl2)が図面と207mm矛盾 | 基礎高(GL+500mm)と1階FL(GL+707mm)を取り違えていた。fl2もfl1+階高で計算していたため同じ誤差を引き継いでいた | 東側立面図の実測値(1階FL=GL+707mm、1階階高2,732mm)に合わせて修正（2026-08-14、詳細は4章） |
| 片流れ屋根レイヤーをオンにすると、屋根が間取りの下に隠れて見える | 全ての半透明マテリアルで`depthWrite:false`にしているため、前後関係は実際のY座標ではなく`renderOrder`の数値だけで決まる。屋根メッシュ(`slopedRoofBox`)だけ`renderOrder`を設定し忘れていて既定値0のまま描画されていた（外皮=1、室内間仕切り=2、ドア/開口部=3より低い） | `slopedRoofBox`に`renderOrder`引数を追加し、屋根を4（他レイヤーより後＝手前）に設定（2026-08-14） |
| `Ryuka-Landscape-Designer`の`data/fixed-site-data.js`にも同じfl1/fl2の誤りがある | 同リポジトリのコメントに「基礎高0.500」と明記されており、`fl1`という変数名でありながら実際は基礎高を表す値として設計されていたと判明。当リポジトリのHTMLは元々ここからLEVELSをコピーしていたため、誤りごと引き継いでいた | 当リポジトリでは4章の通り立面図の実測値に修正済み。`Ryuka-Landscape-Designer`側は未修正（別リポジトリのため対象外）。今後同リポジトリの値を参照する際はfl1/fl2が基礎高基準である点に注意 |
| `node scripts/build-web-data.mjs --check`が、実際にはgenerated/house-data.jsが最新でもSTALEと誤判定することがある | WindowsのGit（`core.autocrlf`）が`.js`ファイルをチェックアウト時にCRLFへ変換するが、Node.jsの`fs.writeFileSync`はLFで書き出す。ファイル内容は実質同じでも、生の文字列比較では改行コードの違いだけで不一致になる | 比較前に`\r\n`を`\n`へ正規化するよう`--check`のロジックを修正（2026-08-15） |
| 表示フロアを1F/2Fに限定していても、非表示側の家具がクリック選択されてしまう | Three.js(r128)の`Raycaster.intersectObject`は`Object3D.visible:false`のオブジェクトを自動的には除外しない。`groups.furniture2`を非表示にしていても、レイキャストは素通りしてヒットする | ヒットしたオブジェクトから祖先を辿り、`visible:false`のノードがあれば除外する`isEffectivelyVisible()`を追加（2026-08-15） |
| `house.json`から`openings`/`interiorDoors`を分離した際、`blender/build_house.py`が旧構造（`data["openings"]`等がhouse.json直下に存在する前提）のまま壊れかけた | データを複数ファイルに分割する変更は、`interior-white-model.html`側の生成パイプライン（`build-web-data.mjs`）だけでなく、Blender側の読み込みロジックも同時に見直す必要があることを見落としやすい。`blender/build_house.py`は開発環境にBlender未導入のため実行確認ができず、気づきにくい | `load_data()`で分離後の3ファイルを読み込み、型カタログを解決してから旧構造と同じ形（`data["openings"]`等）に合成する互換レイヤーを追加（2026-08-15）。**データファイルを分割・移動する変更をするときは、grepで参照箇所を全て洗い出してから着手すること**（今回はBlenderスクリプトを見落としていた） |
| `openings.json`の`offset`は面に沿った「開始端」（西端/北端）であり、窓の中心座標ではない | `note`欄に「中心4.381」等の記載があり中心値だと錯覚しやすいが、実際の中心はoffset+width/2。検証スクリプトを新規に書いた際、offsetを中心として扱い誤ったバグを混入させかけた | 実際の描画ロジック（`x0=o.lx; x1=o.lx+o.w`）を確認してから検証ロジックを実装するよう徹底（2026-08-15） |
| 窓・ドアの壁線スライドで、区画の継ぎ目（例：x=9.100）を一度越えると、越えた側からは元の区画側へドラッグで戻せなくなる「片道の罠」になっていた | `wallRangeForOpening()`が可動範囲を「現在位置が属するfootprint（求積図のゾーン区分）1個」だけから計算していたため、境界を越えて隣のfootprintに入った瞬間、次のドラッグではそちらのfootprintの範囲でクランプされ、越えた方向にしか動けなくなっていた。x=9.100は実際には1本の連続した壁（`1f-a1`〜`1f-a3`が同じ南辺z1=6.370を共有）で、区画分けは求積図上の都合でしかなかった | 現在位置のfootprintから、同じ辺(z0/z1)を共有し隙間なくつながっている区画をすべて合わせた範囲を返すよう修正（2026-08-15、施主の実操作で発覚）。**「1個のfootprintだけで範囲を決める」設計は、区画境界が実在の壁とは限らないこのデータでは常に境界付近で罠になりうる。今後この種の範囲計算をする際は、必ず隣接区画への連続性を確認すること** |
| 斜め框で部屋を分割した際、境界付近だけオレンジ色が濃く表示された | `buildRoomsApprox()`が「頂点4つ＝矩形」と決め打ちし、`polygon.length > 4`のときだけ実ポリゴン(`poly`)を使い、それ以外はバウンディングボックス(`boxWire`)で描画していた。斜め框で分割した2部屋はどちらも頂点4つの台形（矩形ではない）だったため、実形状ではなく外接する四角形で描画され、斜辺付近で2部屋のバウンディングボックスが重なった。半透明マテリアルは重なるほど濃く見えるため（3章の別バグと同じ原理）、境界付近だけ色が濃くなって見えた | 「頂点が4つかどうか」ではなく「全ての辺が軸に沿っているか(`isRectilinear()`)」で判定するよう修正（2026-08-15、施主の実機確認で発覚）。**矩形の判定を頂点数だけで行わないこと。斜めの辺を持つ部屋を今後も追加する可能性があるため、常に実形状で判定する** |
| 開口（アーチ、`operation:'open-arch'`）が、塗りつぶしを付けていたはずなのに平面図モードでも俯瞰モードでもほぼ見えなかった | `archOpeningMesh()`が、天端が円弧の完全に鉛直な板（厚みゼロのShapeGeometry）1枚だけを描画していた。他のドア・開口は`boxWire()`や`BoxGeometry`ベースで実際に厚み（0.06m）のある箱として描いているため、真上から見ても輪郭の分だけ面積が見えるが、この板は厚みが完全にゼロなので、真上から見ると輪郭線ごと一直線に潰れて消える。俯瞰モードでも、カメラの角度・板の向きによっては同様にほぼ視認できない角度になりうる | `open`と同じ矩形の枠線（厚みのある`BoxGeometry`のedges）を必ず重ねて描くよう修正し、板自体もピンクの塗りつぶしをやめて黒線のみに統一した（2026-08-16、施主指摘で発覚）。**厚みゼロの平板ジオメトリは、見る角度によって完全に不可視になりうる。開口・パネル系の要素は、最低限の視認性を保証するために厚みのある形状（箱の輪郭線など）を必ず一緒に描くこと**。ただしこの視認性用の枠線を、アーチ本体と同じ高さ（`d.height`）の箱にしたところ、アーチの立ち上がり（springHeight）より上の箱の角が、俯瞰モードでアーチの輪郭からはみ出して見える二次的な不具合を生んだ（施主が俯瞰スクリーンショットに赤丸で指摘）。**視認性確保だけが目的の補助ジオメトリは、本体の形状と競合しない最小限のサイズ（今回は床面近くの高さ0.05mの薄い箱）に留めること。厚みを持たせること自体は正しい判断でも、「どれだけの厚みが必要か」は本体の形状を踏まえて決める必要がある** |

検討の結果、**「分ける軸が2つあり、それぞれ別の理由で決まる」**という整理で合意した。

- **カタログ（型のライブラリ）は種類（ドア/窓）で分ける**：`data/door-catalog.json`・`data/window-catalog.json`に分割。理由は、施工会社の建具表・サッシ表が実務上も別表であることが多く、ドアと窓は「共通スキーマ」というだけで本質的には別物（ドアは開き勝手が主題、窓は開閉可否が主題）だったため。当初「furniture-catalog.jsonがcategoryフィールド1つで済ませている」ことを理由に1ファイルにまとめていたが、これは技術都合寄りの判断だったと振り返って認めた
- **配置インスタンス（`openings.json`）は位置決めの仕組み（外周/内部）で分けたまま維持する**：exterior側の窓・ドアは`face`+`offset`という位置決めの仕組みが共通で、壁の開口切り欠き処理（`build_exterior_walls`等）や将来の同一壁上の重なりチェックで窓・ドアを同時に扱う必要があるため、無理に分けるとビルドスクリプト側の複雑さが増すだけと判断した

- `door-catalog.json`に3型追加：`door-slide`（引き戸、`operation:slide`）、`door-open`（ドアなしの開口、`operation:open`）、`door-open-arch`（ドアなしの開口・天端アーチ、`operation:open-arch`、追加で`archRise`フィールドを持つ）
- `open`/`open-arch`は`hingeSide`/`swingDir`/`slideDir`を持たせない（`addDoorLeaf()`が扉本体を描かない既存の分岐をそのまま利用できた）。`tests/validate_openings.py`の「開き勝手必須」チェックもこの2種は除外するよう修正
- `open-arch`専用に`archOpeningMesh()`を新設。天端が円弧になった厚みのない平板（door系マテリアルはside:DoubleSideのため厚みなしでも両面から見える）を`THREE.Shape`+`ShapeGeometry`で描画する。orientation別の回転（H=回転なし、V=`rotation.y=-90°`）はtoScene()の符号と合わせて事前に数式で導出し、一時的にテスト用ドアデータ（`data/interior-doors.json`に仮追加→確認後に削除）を使って俯瞰モードのスクリーンショットで実際に検証した

### 2026-08-15：間取りの精細化に着手（第1弾：斜め框による玄関・ホール分割）

窓・ドア編集が一段落したところで、施主から「間取りとして細かく分けられていないところがある（玄関・ホールが1区画のまま、洋室内の収納が区画分けされていない等）」という相談を受けた。

**進め方の相談**：「施主が都度指示する」か「間取りブロックを配置する編集モードを作る」かを検討し、前者を採用した。理由は、部屋の分割は家具・窓ドア編集と違って「既存の枠内で位置調整する」のではなく「1つのポリゴンを線で2つに切る」というトポロジー変更そのものであり、L字形状への対応や`walls`（Blender用の別データ）への波及など、UIとして作り込むには不釣り合いに複雑になる一方、発生頻度は少ない（散発的な精細化作業）ため。施主が平面図のスクリーンショットに線を描き込んで渡す、という元々このプロジェクトで使ってきたピクセル解析の手法をそのまま流用する方針にした（[ARCHITECTURE.md](ARCHITECTURE.md)「rooms / walls について」に方針を記録）。`feature/room-partitions`ブランチで着手。

**第1弾：自宅玄関・ホールの分割**：施主が平面図のスクリーンショットに赤線で分割線（斜め框、目分量の角度）を描き込んで渡してくれた。これを受けて以下を実施。

- この訂正により、階段の一部（最後の直進区間）が1F側では「パントリー（room-1f-21）の天井の上」を通ることになった。パントリーは1Fの実室として存在し続けるが、その真上を2Fへの階段が通過する、いわゆる「階段下収納」の構成になる
- この関係を1F平面図でどう表現するかについて、施主は「一般的な建築図面の表現を参考に、実装可能な方法で」と裁量を渡してくれた。天領住宅の参考図面（階段下部分が破線で示されている）を踏まえ、「上階の構造物が下階の天井裏に隠れて見えないことを示す破線」という建築図面の一般的な慣習を採用した。`stairs`データに`hiddenBelow`（隠れる部屋の矩形）を追加し、`levelFrom`側の平面図記号のうちこの矩形の内側を通る区間だけを`THREE.LineDashedMaterial`で破線描画するようにした（`levelTo`側は階段そのものがその階の実体なので常に実線のまま）。あわせてパントリーのラベルに「（階段下）」を付記し、文字でも明示した
- 内覧モードの歩行判定にも影響があった。階段の経路が今やパントリーの真上を通るため、素直に「経路に近ければ階段」と判定すると、パントリーの中をパントリー自身のドアから歩いているだけなのに、天井裏を通る階段の高さに引っ張られて視点が浮いてしまう不具合が起きる。`stairProgressAt()`に`currentLevel`引数を追加し、「まだ登っていない状態（levelFromのまま）で`hiddenBelow`矩形に入った場合は、階段としては扱わない（＝パントリー自身の床の高さのまま）」という条件を加えて解消した。**上下階を貫く経路と、途中の部屋の天井を素通りする区間が重なるケースでは、「幾何的に近いかどうか」だけでなく「どちらの階として今歩いているか」も判定に含める必要がある**という教訓
- Playwrightで、1F/2F平面図の見た目（廻りが半円になっているか、パントリー部分が破線になっているか）と、パントリーの中を1F視点で歩いた際に視点の高さが浮かないことの両方を検証した

実装を見た施主から、さらに2点フィードバックがあった（「意図はない、指摘に合わせて直してほしい」という前者の階段の話と、ヌックのアーチ開口が見えなくなっているという別件）。

- ヌックの開口（アーチ、`door-006`）が、平面図モードでも俯瞰モードでもほぼ見えなくなっていると指摘された。調査の結果、データ自体は変更されておらず正しく描画処理にも渡っていたが、`archOpeningMesh()`が完全に厚みゼロの鉛直な板1枚だけを描いていたため、真上から見ると輪郭線ごと一直線に潰れて消えるという、この関数が元から持っていた描画上の制約だと判明した（今回のセッションの他の作業がこの関数に触れたことはない）。`open`と同じ矩形の枠線を必ず重ねて描くよう修正し、板の塗りつぶしもピンクをやめて黒線のみに統一した（3章の教訓の表に追記）
- 廻り階段について、最後の直進区間がパントリーの南端まで届いていなかった点は「明確な意図はなく、単に妥当そうな長さで区切っていただけ」と回答し、施主指摘（南端z=1.82まで届くべき）に合わせてそのまま延長した。総段数13は変えず、経路が伸びた分だけ踏み面の奥行きが約135mm→約250mmに改善し、むしろ現実的な寸法に近づいた

ヌックのアーチ開口については、修正後も施主から「強制リロードしたら見えたが、位置が民泊ホール⟷LDK付近（本来あるべき開き戸`door-004`と重なる位置）にずれている」と報告があった。調査するまでもなく、`data/interior-doors.json`の`door-006`は`center:8.22`のままで正本は正しく、Web UI編集機能がブラウザのlocalStorageに古い編集差分を持ったままだったことが原因（本人にStage 2編集パネルの「リセット」ボタンを試してもらったところ、正しい位置に戻った）。**「データファイルは正しいのに表示だけおかしい」という報告を受けたときは、正本のJSONを疑う前に、ブラウザのlocalStorage編集差分（`doorWindowEdits`/`furnitureEdits`）が残っていないかをまず疑うこと**（このアプリのWeb UI編集は正本を直接書き換えず差分として保存する設計のため、こうしたズレが起こりうる）。
