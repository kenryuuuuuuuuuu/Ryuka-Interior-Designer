# 設計・実装・レビューの分担

2026-09-08開始。施主の指定により、GPTが仕様・設計・レビュー、Claude Codeが実装と実行検証を担当します。進行順は [実装ロードマップ](IMPLEMENTATION_ROADMAP.md)、最初の指示は [W01](tasks/W01-render-startup.md) です。

## 役割と情報の置き場所

- 施主：目標・優先順位・実物の仕様を決定し、見え方と操作感を確認します。
- GPT：問題の分解、データ契約、失敗時の挙動、受入条件、レビューを担当します。通常の実装を並行して進めません。
- Claude Code：仕様内の実装方法を選び、実装・検証・簡潔な完了報告を行います。仕様の穴は具体的な選択肢と影響を報告します。
- 共通規則はAGENTS.md、構造はARCHITECTURE.md、現況はSTATUS.md、今回の契約は `docs/tasks/<ID>.md`。会話だけに決定事項を残しません。

詳細設計は次の1件に絞ります。遠い段階は成果・依存関係・完了条件を先に固定し、直前に詳細化します。実装者に行単位の指示はせず、守るべき契約と具体的な失敗例を渡します。

## 1件の進め方

1. GPTが [仕様テンプレート](tasks/TEMPLATE.md) を埋め、状態をREADYにします。施主の合意済み範囲なら定型作業ごとの再承認は不要です。
2. Claude Codeは対象ワークツリー、ブランチ、未コミット変更を確認します。開始時の完全なコミットSHAをBASEとして報告に固定します。mainに戻したり、未関連変更をまとめてコミットしたりしません。別機能は別ブランチ/ワークツリーにします。
3. 受入条件に沿って実装します。データ契約・正本・範囲を変える必要があれば、理由と代案を報告してその変更を保留します。仕様を緩めてテストだけ通すことは禁止です。仕様内の通常の修正は継続できます。
4. [報告テンプレート](tasks/REPORT_TEMPLATE.md) を `<ID>-report.md` として作成し、コードと一緒にコミットします。ローカル生成物・ログ・画像はbuild配下に残し、公開資料には個人情報を載せません。
5. `prepare-review.py` でBASEからHEADまでの差分一式を作ります。施主はGPTにタスクID・レビュー用ディレクトリだけを渡せます。同じリポジトリを読めない環境なら、その差分一式とmanifestに列挙した必要な証拠ファイルを受け渡します（スクリプトは証拠本体をコピーしません）。
6. GPTは報告の要約だけで判断せず、全変更ファイル一覧と差分、影響先、受入条件の証拠を確認します。[レビューテンプレート](tasks/REVIEW_TEMPLATE.md)から結果を `<ID>-review.md` に残し、対象HEAD、条件別判定、重大度、修正対象、未確認事項を明記します。判定はACCEPTED / CHANGES_REQUESTED / BLOCKEDです。
7. 修正は同じBASEから累積差分を再提出します。レビュー済みHEAD以後の変更は再レビュー対象です。mainとの差分が増えた場合は統合後の検証も必要です。レビュー合格は自動push/mergeの指示ではありません。

## 変更漏れを減らす仕組み

```powershell
# 完了報告を含め、対象変更をコミットしてから実行します。
# BASE_SHAは開始時に記録した完全なSHAへ置換します。
python scripts/prepare-review.py --base BASE_SHA --output build/reviews/W01-v1 --artifact build/refresh-walk-v3/ue/walkthrough-verification.json
```

出力はコミット範囲、全変更パス（削除・バイナリを含む）、完全な差分、指定証拠ファイルのSHA-256です。未コミット/未追跡ファイルがあれば拒否します。build等のignoredファイルはGit差分に含まれないため、報告で使用した証拠を `--artifact` で個別指定してください。巨大なblendを毎回読む必要はありませんが、使用したもののハッシュと再生成入力は記録します。出力はローカル限定で、自動送信しません。

この仕組みが保証するのは指定したGit範囲の変更の列挙です。仕様の理解・レビューの正しさを100%保証するものではありません。未指定のignoredファイル、OS/Engine/ドライバの変更は自動検出対象外なので、環境変更も報告必須です。ハッシュは証拠の同一性を示し、テスト成功やそのコードから生成された事実までは証明しません。各実行に入力・コード版・コマンド・結果を紐づけます。

## 検証と消費を抑える運用

- GPTへの通常の受け渡しは、着手前の設計と完了時のレビューの2回です。障害・仕様変更時のみ途中相談します。
- 報告は受入条件ごとの結果を中心にし、生ログを会話へ貼りません。GPTは必要な箇所だけ追加で読みます。
- 検証は変更の影響範囲で選びます。未実行はNOT_RUN、環境で実行不能はBLOCKEDと書き、成功扱いにしません。描画なしテストを描画・手動操作の合格に代用しません。
- コミット前のhouse検証と、仕様が指定する回帰チェックは省きません。バグ修正は可能なら修正前に失敗する再現テストを添えます。
- 同じ失敗で新しい証拠が得られない検証を繰り返さず、異なる仮説を2回検証して進展がなければ、判明点・否定した仮説・次に必要な情報を報告します。
- モデル変更時も会話全文ではなくタスク・報告・差分を渡します。実際の削減量は数件運用して再作業回数と利用状況から見直します。

## モデルの選択（2026-09-08時点の推奨）

基本は **Sonnet 5** です。仕様と再現テストがあるPython/JS/C++実装、データ移行、UI、回帰修正を任せます。言語がC++という理由だけでOpusにはしません。

**Opus 5** は原因不明のUE/Windows境界の調査、複数層にまたがる未解決問題に使います。最初のW01はこれに該当します。原因が絞れた後の定型実装はSonnetへ戻せます。実装品質はこのプロジェクトの受入条件で判断します。

公式情報：[Sonnet 5](https://www.anthropic.com/news/claude-sonnet-5)、[Opus 5](https://www.anthropic.com/news/claude-opus-5)。能力・用途の説明を参考にしたプロジェクト固有の判断であり、所要時間や費用の保証ではありません。Claude Codeで実際に選択されたモデルを確認して報告してください。
